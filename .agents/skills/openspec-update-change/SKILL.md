Локализованная адаптация skills, созданных `openspec init --tools codex` версии 1.17.0.
Работай на русском языке, соблюдай AGENTS.md и контекст openspec/config.yaml.
Команды, JSON-поля, идентификаторы артефактов и служебные маркеры не переводи.

Перед записью выполни `openspec list --json`, проверь `root`. Если корня нет,
не создавай его побочно: при явном запросе OpenSpec уточни настройку у пользователя,
иначе выполни задачу без OpenSpec. Ошибки декларации store покажи вместе с `fix`.
Если выбран store, найди его через `openspec store list --json` и сохраняй
`--store <id>` во всех поддерживающих его командах до конца операции.
Используй пути из JSON CLI, а не предположения о расположении файлов.
Если имя change не задано, используй однозначный контекст или единственный change;
при неоднозначности покажи `openspec list --json` и предложи выбрать.
Не придумывай игровые правила: неясности согласуй с владельцем до реализации.

1. Получи `openspec status --change "<name>" --json`. Используй идентификаторы
   схемы и конкретные `artifactPaths.<id>.existingOutputPaths`.
2. Перечитай все существующие артефакты. Подготовь изменения и проверь согласованность
   в обоих направлениях: design может потребовать обновления proposal/specs.
3. Покажи каждую правку с причиной и получи подтверждение перед записью.
   Для существенного пересмотра запроси `openspec instructions <id> --change "<name>" --json`.
4. Не создавай отсутствующие артефакты и не трогай skipped. Исключение: согласованный
   конкретный файл внутри уже частично заполненного glob-артефакта. Перед созданием
   обнови status/instructions, проверь путь внутри changeRoot с учётом symlink,
   создай только если файл ещё отсутствует. Никогда не пиши по glob-шаблону.
5. Не меняй код. При смене цели предложи отдельный change. Покажи исправления,
   отклонённые предложения и оставшиеся шаги. Не запускай следующий workflow сам.
Команда `openspec update` обновляет сгенерированную интеграцию, а не план change.

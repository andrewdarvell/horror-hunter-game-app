# Правила работы с репозиторием

## Структура проекта и модули

HorrorHunterGame — игра на Java и libGDX с четырьмя модулями Gradle:

- `domain/src/main/java/ru/darvell/game/hhg/domain/` — основной модуль для независимых от платформы моделей и правил игры. При компиляции использует только Lombok.
- `core/src/main/java/ru/darvell/game/hhg/` — интеграция с libGDX. Класс `Main` создаёт начальный экран `FirstScreen`. Модуль зависит от `domain`.
- `lwjgl3/src/main/java/` — запуск настольной версии и вспомогательный код. Значки и ресурсы находятся в `lwjgl3/icons/` и `lwjgl3/src/main/resources/`.
- `android/src/main/java/` — запуск версии для Android. Ресурсы и манифест находятся в `android/res/` и `android/AndroidManifest.xml`.
- `assets/` — общие игровые ресурсы; пока здесь только файл-заглушка. Gradle создаёт `assets/assets.txt`: не редактируйте и не добавляйте этот файл в коммиты.

## Сборка, тестирование и запуск

Запускайте команды из корня репозитория через включённый в проект Gradle Wrapper (`gradlew.bat` в Windows). Конфигурация Gradle использует JDK 21, а исходный код рассчитан на Java 8. Для сборки Android нужен Android SDK с платформой 36.

- `./gradlew lwjgl3:run` — запустить настольную версию с рабочим каталогом `assets/`.
- `./gradlew lwjgl3:jar` — собрать исполняемый JAR в `lwjgl3/build/libs/`.
- `./gradlew build` — собрать все модули и выполнить настроенные проверки.
- `./gradlew domain:test` — запустить JUnit 5-тесты `domain`; в `core` тесты пока не настроены.
- `./gradlew android:assembleDebug` — собрать отладочный APK.
- `./gradlew android:lint` — запустить статическую проверку Android.

## Стиль кода и имена

Следуйте `.editorconfig`: UTF-8, переводы строк LF, пробелы вместо табуляции и перевод строки в конце файла. Для Java используйте отступ в четыре пробела, для Gradle — в два. Удаляйте пробелы в конце строк, кроме случаев, когда они нужны в Markdown. Отдельный форматировщик не настроен.

Называйте классы в `UpperCamelCase`, методы и поля — в `lowerCamelCase`. Используйте имена пакетов в нижнем регистре под `ru.darvell.game.hhg`. Сохраняйте совместимость с Java 8. Освобождайте ресурсы libGDX в соответствующих методах жизненного цикла.

## Тестирование

В `domain` настроен JUnit Jupiter 5.13.4 с JUnit Platform и инфраструктурным `JUnitPlatformSmokeTest`; запуск: `./gradlew :domain:test`. Требований к покрытию нет. Добавляйте модульные тесты в `domain/src/test/java/` или `core/src/test/java/` в зависимости от расположения проверяемого кода. Повторяйте структуру пакетов исходного кода и называйте классы `*Test`. В `core` тестовый фреймворк пока не настроен. После изменений игрового процесса вручную проверяйте запуск настольной версии, отрисовку, изменение размера окна и соответствующее поведение на Android.

## Процесс разработки: SDD, OpenSpec и Codex

Мы используем **гибридный Spec-Driven Development (SDD)**. Подробные правила: [DEVELOPMENT_WORKFLOW.md](https://github.com/andrewdarvell/horror-hunter-game-design/blob/main/docs/DEVELOPMENT_WORKFLOW.md). Архитектурные границы: [ADR-001](https://github.com/andrewdarvell/horror-hunter-game-design/blob/main/docs/architecture/ADR-001-hexagonal-architecture.md).

- **До реализации** уточняйте ожидаемое поведение, границы задачи и критерии приёмки. Не приступайте к нетривиальным изменениям, если требования не определены.
- **Новые игровые механики и изменения правил** ведите через OpenSpec: согласованные `proposal` и `specs`, затем технический `design`, `tasks` и реализация. Используйте принятый в проекте workflow OpenSpec после его настройки.
- **Мелкие технические правки** без изменения поведения можно выполнять по короткому плану с проверяемым результатом. Для багов фиксируйте воспроизведение, ожидаемое поведение и регрессионную проверку. Неопределённые технологии сначала изучайте отдельным spike.
- **Не меняйте игровые правила молча.** Если техническая реализация обнаружила пробел или противоречие в требованиях, предложите уточнение и дождитесь решения владельца проекта; затем обновите спецификацию.
- **Код и требования синхронизированы:** изменившееся поведение должно отражаться в OpenSpec. Завершённые изменения после приёмки синхронизируются с актуальными `openspec/specs/` и архивируются; не выдавайте незавершённые фичи за реализованные.
- **Соблюдайте гексагональную архитектуру:** `domain` не зависит от libGDX, платформ и сторонних адаптеров; интеграции реализуются снаружи через порты по необходимости. Не создавайте интерфейсы для каждой библиотеки ради формальности.
- **К каждой существенной задаче** прилагайте соответствующие тесты и отчёт о выполненных проверках. Если запуск или сборка недоступны, укажите это явно; не утверждайте, что тесты прошли.
- **Работайте тематическими изменениями:** отдельная ветка/PR для существенной фичи, осмысленные коммиты, описание связи с требованиями и проверок. Для графики добавляйте скриншоты или записи по возможности.
- **Документация и требования на русском**; имена в исходном коде, названия библиотек и общепринятые технические обозначения — на английском.

OpenSpec 1.17.0 инициализирован для Codex: `openspec/config.yaml` и `.agents/skills/openspec-*`. Начало будущего изменения: `$openspec-propose <описание>`; инструкции по установке CLI и проверкам — в [openspec/README.md](openspec/README.md). Тестовый фреймворк настроен только в `domain`.

## Коммиты и запросы на слияние

История Git в этой копии недоступна, поэтому существующие соглашения об именах коммитов проверить нельзя. Пишите короткие темы в повелительном наклонении, например `Add player movement`, и сохраняйте каждый коммит тематически цельным.

В описании запроса на слияние указывайте изменённое поведение, ссылки на связанные задачи и выполненные проверки. Для визуальных изменений добавляйте снимки экрана или записи. Пути к Android SDK храните в игнорируемом файле `local.properties`; не включайте в коммиты результаты сборки и нативные библиотеки.

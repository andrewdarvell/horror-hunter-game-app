# Change: domain-package-structure

## Why

После четырёх игровых вертикальных срезов доменные классы геометрии, участников, тактики и координации сцены оказались в единственном пакете `ru.darvell.game.hhg.domain.world`. Это скрывает границы ответственности и позволит будущим механикам разрастаться в «общем чулане». Теперь, пока набор классов небольшой, пора разложить его по предметным пакетам.

**Срез исключительно структурный:** игровое поведение, API на уровне сценариев, формулы, время и графика не меняются. На момент составления proposal PR #12 смёржен, `tactical-mode-entry` присутствует в основных specs.

## What Changes

Предлагаемая целевая структура внутри `domain/src/main/java/ru/darvell/game/hhg/domain/`:

| Пакет | Классы | Ответственность |
| --- | --- | --- |
| `world` | `WorldPosition`, `WorldGeometry`, `StaticAabb` | Мировые координаты и статические препятствия |
| `actor` | `HunterState`, `CreaturePatrolState` | Состояние и поведение персонажей в исследовании |
| `tactical` | `TacticalGrid`, `CellCoordinates`, `TacticalPlacement`, `TacticalEntryPlanner`, `TacticalEntryResult` | Сетка, клеточная занятость и безопасная расстановка |
| `scene` | `WorldSceneState`, `SceneMode` | Координация участников и переключение режимов |

Сохраняем эти имена классов. Если при planning обнаружится конкретный цикл на уровне пакетов, предложить **минимальную коррекцию размещения класса** с объяснением, а не создавать `common`/`utils` для всех типов.

Зависимости направлены преимущественно `scene → actor/tactical/world`, `actor → world`, `tactical → world`. `world` не зависит от персонажей и тактики; `actor` не должен импортировать `scene` или `tactical`, а `tactical` не должен импортировать `scene` или `actor`.

Переместить Java-файлы и связанные с ними JUnit-тесты в соответствующие пакеты; обновить package/import, ссылки в `core`, все call sites, документацию/README, где упоминаются прежние FQCN. **Не** переименовывать классы и не переписывать алгоритмы ради рефакторинга.

### Особое внимание: package-private контракт

Сейчас `WorldSceneState` вызывает package-private методы `HunterState.applyTacticalPosition`, `CreaturePatrolState.applyTacticalPosition`, `CreaturePatrolState.checkDetection`, `CreaturePatrolState.advancePatrol`. После разнесения по `scene` и `actor` эти вызовы перестанут компилироваться.

Нельзя исправить проблему механическим превращением всех четырёх методов в публичные произвольные setters. В `design.md` **до реализации** выбрать и обосновать минимальный способ координации:
- сохранить единый источник текущих мировых позиций, владение участниками внутри сцены и атомарность применения тактической расстановки;
- не позволять `core` случайно обходить сцены/режим;
- не вводить фиктивный `IActor`, глобальный сервис, reflection, `internal`-подобные package-name трюки, новый framework или фабрики с избыточной иерархией;
- если небольшой публичный семантический метод действительно необходим из-за Java package boundaries, зафиксировать, **какой инвариант он проверяет** и почему этот API безопаснее сырого `setPosition`;
- отдельно проверить атомарность, сохранение состояния патруля и отсутствие обходного обновления из `core`.

**Главная цель — смысловые границы, а не архитектура ради архитектуры.** Возможно, нужны небольшие изменения сигнатур/инкапсуляции, но не изменение поведения.

## Out of scope

- Новые игровые механики, существа, боевые ходы, инициативы, движение по клеткам.
- Изменение размера тактической клетки, радиуса обнаружения, числа препятствий, скорости или позиции существ.
- Анимация перехода в тактический режим, движение камеры, изменение рендера и UI.
- Замена Java/libGDX, новая система dependency injection/ECS, отдельные Gradle-модули.
- Обобщение одного `CreaturePatrolState` в систему AI и выделение отдельного `monster`/ `hunter` пакета для одного класса.

## Acceptance Criteria

1. Все перечисленные production-классы лежат в выбранных пакетах; в `domain.world` остались только геометрия и пространственные типы. Дерево пакетов читается как `world / actor / tactical / scene`.
2. Нет импортов из `world` в `actor`, `tactical` или `scene`; нет циклических пакетных зависимостей. `domain` не зависит от libGDX.
3. Сохраняются все принятые игровые правила: WASD и коллизии, патруль и обнаружение, LOS, вход в тактику по обнаружению и T, расстановка по двум клеткам, безопасный snap/отказ, заморозка симуляции, last-seen и debug G.
4. В `core` используются новые классы/импорты, но не появляется новый путь к изменяемым внутренним состояниям участников. `FirstScreen` не начинает обходить `WorldSceneState`.
5. Решение доступа между `scene` и `actor` документировано; публичные безусловные setters не добавлены; тесты подтверждают инварианты после перехода и при отказе.
6. Все действующие JUnit-тесты перенесены в релевантные пакеты, сохраняют сценарии и assertions, не теряется покрытие package-private семантики. Новые tests допускаются для доступа и инкапсуляции, но не требуется полное переписывание тестов.
7. `./gradlew :domain:test :core:classes :lwjgl3:classes` выполняется успешно; число успешно выполненных тестов не меньше baseline (на PR #12 сообщалось о 89). Android compilation дополнительно по возможности.
8. `openspec validate domain-package-structure --strict --no-interactive` проходит; `git diff --check` чистый. Не утверждать ручную проверку без фактического запуска.
9. Изменение оформлено отдельным PR, с понятным diff: преимущественно package declarations, imports и перемещения. При необходимости дополнительные правки инкапсуляции чётко отделены и объяснены.

## OpenSpec

Новая capability **не нужна**: смена пакетных путей без изменения игрового поведения не является новой механикой. В planning подобрать минимальную форму требований/спецификации для архитектурного change в используемой OpenSpec schema, не переписывая уже принятые `world-navigation`, `creature-patrol`, `creature-detection`, `tactical-mode-entry` ради FQCN. В `design.md` зафиксировать границы пакетов, зависимостей и решение package-private доступа; в `tasks.md` — порядок безопасного переноса с тестами.

## Notes for Codex

- Изучи актуальные файлы и тесты из `main`, `AGENTS.md`, ADR-001.
- До реализации согласуй выбранное решение cross-package access на ревью planning. Избегай открытых setters и излишних абстракций.
- Сохраняй поведение и публичные сценарии; не смешивай с запланированными изменениями масштаба сетки и визуальной анимацией.
- После одобренного planning — отдельная реализация и автоматические тесты; sync/archive только после приёмки владельцем.

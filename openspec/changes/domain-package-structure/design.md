## Context

Мотивация и границы изменения — в `proposal.md`. Все 12 production-типов сейчас находятся в `domain.world`. Изучены текущие классы, `WorldSceneStateTest`, call sites `FirstScreen` и ADR-001 из соседнего design-репозитория.

Java package-private доступ действует только внутри одного пакета: подпакет `scene.actor` не получает доступ к `scene`. Разделение состояний участников и координатора ломает четыре вызова: два `applyTacticalPosition`, `checkDetection` и `advancePatrol`. Тесты дополнительно используют package-private диагностику патруля и внутренние helpers planner.

Документ описывает будущую реализацию. Разрешение подготовить документы не является разрешением начать её.

## Goals / Non-Goals

**Goals:** выделить геометрию, чистое тактическое планирование и изменяемую сцену; сохранить доступ, порядок операций, существующие сигнатуры методов и проверяемые инварианты.

**Non-Goals:** усиление владения через новый construction API, новые публичные методы мутации, интерфейсы, callbacks, дополнительные Gradle-модули. Игровое поведение, размер клетки, константы и анимации не меняются.

## Decisions

### 1. Пакет — граница совместной мутации

| Пакет относительно `ru.darvell.game.hhg.domain` | Классы | Граница ответственности |
| --- | --- | --- |
| `world` | `WorldPosition`, `WorldGeometry`, `StaticAabb` | Пространственные значения, препятствия, коллизии, LOS |
| `tactical` | `TacticalGrid`, `CellCoordinates`, `TacticalPlacement`, `TacticalEntryPlanner`, `TacticalEntryResult` | Сетка и чистый расчёт расстановки без мутации участников |
| `scene` | `WorldSceneState`, `SceneMode`, `HunterState`, `CreaturePatrolState` | Изменяемые участники и координация их жизненного цикла |

Корректируем исходное предложение `scene / actor`: состояния участников остаются вместе с координатором в `scene`. Отдельного пустого `actor` не создаём. Граница обусловлена совместной мутацией и существующим доступом, а не наличием пакетного цикла. Имена классов и их ответственность сохраняются.

Разрешённые зависимости production-пакетов:

```text
scene ──→ tactical ──→ world
  └─────────────────→ world
```

`world` не знает о сцене или тактике; `tactical` не знает об участниках и сцене. Обратные импорты, включая зависимости через сигнатуры и полные имена типов, запрещены. `domain` остаётся чистой Java 8 без libGDX, платформ и адаптеров. `core` собирает компоненты, обрабатывает ввод и отображает состояние — согласно ADR-001. Новых портов для переноса классов не требуется.

### 2. Сохранить существующую поверхность доступа

Четыре метода координации остаются package-private. Диагностические `getTargetIndex`, `getDirection`, `getWaitRemaining` также не становятся публичными. Новых setters нет; текущие публичные `HunterState.move` и `CreaturePatrolState.update` сохраняются для существующих сценариев использования самостоятельных состояний.

Сцена не возвращает изменяемые состояния участников. Позиции остаются единственным источником истины внутри участников; placement описывает занятость клеток и не становится второй независимо обновляемой позицией.

Текущее владение является контрактом использования: конструктор получает внешние ссылки, а не обеспечивает исключительное владение средствами языка. После передачи в сцену `FirstScreen` не сохраняет участников в полях и не обновляет их напрямую. Это проверяется по call sites; не заявляем compile-time запрет для существующих публичных `move`/`update`. Создание read-only interfaces, копирование состояний и изменение конструктора отложены.

Рассмотренные альтернативы:

- Сделать четыре метода публичными: открывает независимые фазы координации и произвольное применение позиций. Проверка конечности координат не доказывает режим сцены или согласованность двух участников.
- Передавать actor публичный результат тактического планирования: добавляет зависимость `actor → tactical`, не подтверждает актуальность результата и не решает парное применение само по себе.
- Добавить посредника, token, callback или интерфейс: увеличивает API и число сущностей ради доступа, который уже корректно ограничен одним пакетом.
- Использовать подпакет, reflection или наследование: подпакет не даёт доступа, остальные варианты усложняют модель без пользы для текущего рефакторинга.

### 3. Сохранить последовательность и границу атомарности

`update` сохраняет текущий порядок: валидация входа → ранний выход для tactical → движение охотника → обнаружение → попытка входа при первом обнаружении или ручном запросе → патруль, если режим остался exploration. Нельзя заменить отдельные фазы вызовом `CreaturePatrolState.update`: он продвинет патруль до решения сцены о переходе.

`enterTactical` сначала проверяет текущий режим и полностью рассчитывает план без мутации. При `SUCCESS` остаются прежние присваивания: позиция охотника, позиция существа, placement, режим. Между ними не добавляются валидации, callbacks, события или другие потенциально падающие операции. При отказе planner этот метод не меняет участников, metadata патруля, placement или режим.

Атомарность относится к наблюдаемому результату одной операции в существующей последовательной симуляции. Многопоточная транзакционность не вводится. Отказ входа из `update` не откатывает уже выполненное движение охотника и обнаружение. При ручном отказе не встревоженный патруль продолжает шаг; после обнаружения состояние alerted сохраняется, автоматический повтор без нового первого обнаружения не добавляется.

Успешный snap не меняет target index, направление, остаток паузы, alerted и last-seen. Last-seen сохраняет замеченную позицию до snap. В tactical обновление заморожено; повторный запрос сохраняет `ALREADY_TACTICAL`.

### 4. Перенести тесты вместе с проверяемой ответственностью

| Пакет тестов | Классы |
| --- | --- |
| `world` | `StaticAabbTest`, `WorldGeometryTest`, `WorldGeometryPathTest`, `WorldGeometryLineOfSightTest` |
| `tactical` | `TacticalGridTest`, `TacticalEntryPlannerTest` |
| `scene` | `HunterStateTest`, `CreaturePatrolStateTest`, `CreatureDetectionTest`, `WorldSceneStateTest` |

`JUnitPlatformSmokeTest` остаётся в корневом пакете `domain`. Assertions и сценарии сохраняются. Package-private helpers, Candidate и factories результата остаются в `tactical`; диагностика участников доступна тестам `scene`.

Особый случай: `WorldSceneStateTest` сейчас вызывает package-private `TacticalEntryPlannerTest.blockedCentersExcept`. После разделения тестовых пакетов перенести необходимую fixture в private helper самого `WorldSceneStateTest`, сохранив её геометрию. Небольшое дублирование test fixture предпочтительнее публичного API production или зависимости одного test-класса от другого. Не ослаблять assertions ради компиляции.

### 5. Не создавать фиктивные игровые specs

Использовать `skip_specs: true` в `.openspec.yaml`, как предусмотрено инструкциями OpenSpec 1.17.0 для изменений без spec-level поведения. Новых capabilities и delta specs нет. Существующие specs навигации, препятствий, патруля, обнаружения и входа в тактику остаются критерием регрессии. Архитектурное решение проверяется по этому design и acceptance criteria proposal.

## Risks / Trade-offs

- `scene` включает и координатор, и участников → это намеренная граница package-private доступа; выделение `actor` потребует отдельного обоснованного контракта при появлении реальной необходимости.
- Сохранённые внешние ссылки позволяют нарушить владение → проверить все production call sites; текущую гарантию не выдавать за строгую изоляцию.
- Перенос тестов может скрыть потерю сценариев → сравнить перечень тестов и число успешно выполненных с baseline; сохранить assertions и диагностику патруля.
- Ошибочная трактовка отказа как rollback всего кадра → отдельно сохранить тесты отказа `enterTactical` и отказа внутри `update`.
- FQCN меняются → обновить все потребители в репозитории; совместимость старых бинарных имён и deprecated wrappers не вводится.

## Migration Plan

После ревью planning и отдельного запуска реализации: зафиксировать baseline, перенести классы и тесты согласно таблицам, исправить imports и fixture, проверить core и документацию, выполнить проверки из `tasks.md`.

Не создавать смешанные временные production-копии классов. Изменение оформить тематической веткой/PR; откат — обратное тематическое изменение перемещений и imports. Данных для миграции нет. Синхронизация и архивирование OpenSpec — только после приёмки реализации. На этапе подготовки документов сборка и ручной запуск игры не выполнялись.

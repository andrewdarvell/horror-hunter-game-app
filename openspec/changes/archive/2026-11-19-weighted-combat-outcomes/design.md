## Goals / Non-Goals

Цель design — определить один небольшой API, численный контракт и проверяемую последовательность подготовки. API представляет данные и выбор, не систему правил.

За пределами: конфигурационные файлы, сериализация/replay format, журнал модификаторов, общий effect engine, модель последствий, собственный RNG, система характеристик и любые изменения игровых классов. Числа fixtures иллюстрируют контракт, не баланс. Конкретные эффекты усталости, крови, репутации и суеверий здесь не утверждаются.

## Decisions

### P1 — Строковые идентификаторы и immutable snapshots

Новый пакет `ru.darvell.game.hhg.domain.combat.outcome`, три final-класса без наследования:

| Класс | Ответственность и предлагаемый Java 8 API |
| --- | --- |
| `WeightedOutcome` | `WeightedOutcome(String id, double weight)`, `getId()`, `getWeight()`; immutable value object с value equality |
| `OutcomeTable` | `of(List<WeightedOutcome>)`, `getOutcomes()`, `add(WeightedOutcome)`, `remove(String)`, `replace(String, WeightedOutcome)`, `filter(Predicate<String>)`, `withWeight(String, double)`; каждый метод преобразования возвращает новый snapshot |
| `WeightedOutcomeResolver` | Stateless utility с `static String resolve(OutcomeTable table, DoubleSupplier random)` |

`OutcomeTable.of` делает defensive copy, выдаёт unmodifiable list. Порядок — порядок списка, поиск по id через линейный проход; при обычных 2–3 элементах индекс или отдельный registry не нужен. Идентификатор — непустая строка без пробелов по краям (`id.equals(id.trim())`); регистр значим. Объекты и коллекции не принимают null. Вес проверяется при создании исхода и каждой его замене: `Double.isFinite(weight) && weight >= 0`; -0.0 канонизируется в +0.0.

Пустая таблица и таблица с нулевой суммой допустимы как промежуточные snapshots. Только resolver требует непустого набора с положительной суммой. Это позволяет удалить последний вариант и затем добавить новый, не вводя builder.

Возвращаем только `String`, без debug-весов, списка эффектов и outcome enum. Внешний потребитель сам сопоставляет id с будущими последствиями. Строки проще generic payload, который мог бы случайно протащить исполняемые эффекты или типы интеграции.

### P2 — Явная последовательность вместо modifier engine

Порядок подготовки принадлежит вызывающей доменной логике:

1. Создать базовую таблицу типа столкновения.
2. Последовательно применить add/remove/replace по релевантному контексту; add добавляет в конец, replace сохраняет позицию.
3. `filter(allowedIdPredicate)` исключает физически невозможные исходы, сохраняя порядок. Predicate вычисляет будущая контекстная логика из снимка ситуации; ядро знает только id.
4. Применить `withWeight` только к оставшимся id; затем вызвать resolver. Если снова менялся состав, повторить физический допуск перед модификацией весов.

Повторные изменения одного веса выполняются в порядке вызовов: последнее значение заменяет предыдущее. Отдельного приоритета, автообъединения, стека эффектов, DSL и реестра модификаторов нет. При необходимости caller вычисляет `oldWeight * factor` или `oldWeight + delta` обычной Java и передаёт результат в `withWeight`. Отрицательный, бесконечный или NaN результат отклоняется; clamp к нулю отсутствует. Формулы игровых модификаторов должны согласовываться отдельно.

Добавить существующий id, удалить/заменить/изменить отсутствующий id, заменить на чужой существующий id — `IllegalArgumentException`. Замена с прежним id разрешена. Несколько модификаторов могут работать с одной таблицей по очереди, но не зависят от порядка обхода HashMap. Predicate должен быть pure и стабильным; исключение из него распространяется, исходный snapshot не меняется.

Трёхфазный протокол — контракт caller, не дополнительная иерархия phase-типов. Resolver принимает уже физически допустимый набор, как предусмотрено proposal. Он не способен проверить геометрию самостоятельно. `withWeight` отсутствующий id не создаёт, поэтому вес не возрождает исключённый результат. Добавленные/заменённые варианты проходят фильтр вместе с базовыми.

Тестовые функции с условным flag могут показать изменение [50,30,20] → [25,30,45] и добавление/исключение d. Flag не представляет игровую степень усталости, а таблица не является конкретной реакцией волка. Механизм не превращает услышанный слух в факт и не определяет, кто знает репутацию. Выбор AI до столкновения остаётся внешней системой.

### P3 — double снаружи, точное десятичное сравнение внутри

`int/long` необоснованно ограничат дробные модификаторы; наивная сумма double может переполниться, а накопление округлённых вероятностей делает границы неоднозначными. Выбираем конечные double как компактный вход, а в resolver используем `BigDecimal.valueOf(weight)` и точные `add/multiply/compareTo` без `MathContext` и деления.

Числовая семантика — каноническая десятичная запись переданного double, а не его точная двоичная дробь. Например, переданные 0.1 и 0.2 трактуются как 0.1 и 0.2; уже вычисленное caller значение `0.1 + 0.2` остаётся 0.30000000000000004. Механизм не исправляет вычисления caller и не обещает инвариантность после округляющих/переполняющихся преобразований double.

Алгоритм (O(n) времени, O(n) временных данных, без ограничения числа исходов кроме памяти):

1. До RNG проверить table/random на null, получить положительные веса в исходном порядке и точную сумму S. Пустая таблица или S = 0 — ошибка конфигурации.
2. Если положительный вес один — вернуть его id без RNG, даже если в таблице несколько нулевых элементов.
3. Иначе вызвать `random.getAsDouble()` ровно один раз; проверить конечность и `0 <= u < 1` (-0.0 эквивалентен 0).
4. Вычислить `target = BigDecimal.valueOf(u).multiply(S)` точно.
5. Накопить положительные веса и вернуть первый id с `cumulative.compareTo(target) > 0`. Равенство отдаёт границу следующему положительному исходу.

Это нормализация через эквивалентность `u < cumulative / S` и `u * S < cumulative`; деление и хранение округлённых вероятностей не нужны. Математические вероятности `w / S` в сумме равны 1. Например, S=100 даёт [0,0.5), [0.5,0.8), [0.8,1). Пары MAX_VALUE и MIN_VALUE корректны без overflow/underflow суммы. Нулевые элементы не создают интервалов. Недостижение последнего элемента при валидном u математически невозможно; защитная проверка реализации должна сигнализировать внутреннюю ошибку, а не выбирать запасной id.

Дискретная сетка double RNG означает, что крайне узкий положительный интервал может не содержать представимого отсчёта. Это ограничение источника, а не округление весов; не обещаем достижимость любого положительного веса произвольного масштаба с double RNG. Детерминированная проверка каждого исхода выполняется на репрезентативных таблицах. Числа 50/30/20 — только fixture.

### P4 — Стандартный функциональный контракт RNG

Используем Java 8 `java.util.function.DoubleSupplier`, без собственного интерфейса с той же сигнатурой и без внешних зависимостей. Это узкая точка подмены по ADR-001: lambda для теста, `seededRandom::nextDouble` для проверки replay. Seed и жизненный цикл источника принадлежат caller; resolver не вызывает `Math.random()`, не создаёт `Random`, не читает часы и не хранит скрытого состояния.

Ошибка конфигурации и null-источник — `IllegalArgumentException` до RNG. Некорректный отсчёт — та же ошибка после одного вызова; повторов нет. Исключение самого supplier распространяется как есть. Детерминированность гарантирована для одинаковых упорядоченных финальных таблиц и одинаковой последовательности отсчётов/вызовов, не для произвольного переставленного набора. Immutable snapshots можно переиспользовать; потокобезопасность supplier остаётся ответственностью caller. Подготовка не расходует RNG.

Единственный положительный исход расходует ноль отсчётов: это явное исключение к «одному выбору» из proposal, критерий 4, и §8.4. Поэтому здесь нет изменения игрового правила.

### P5 — Только библиотечная граница

Все три класса и unit tests — внутри `domain`; используются только JDK-типы. `domain` не зависит от libGDX, платформ, `core` или адаптеров. Новых Gradle-зависимостей не требуется. Generic resolver ничего не знает о `WorldSceneState`, `TacticalAttackResult.Outcome`, `PrototypeBiteState`, конкретных существах, оружии или эффектах.

Будущий событийный движок сможет подготовить таблицу, получить id и найти описание последствий в своей таблице. Pure test с условным `Map<String,String>` демонстрирует эту границу без применения damage/recovery. Не добавляем integration adapter сейчас, не меняем preview и расход RNG в прототипной схватке. Работа не затрагивает PR #37 и не требует его merge.

### P6 — Проверяемая приёмка

JUnit 5 в новом пакете `domain/src/test/java/ru/darvell/game/hhg/domain/combat/outcome/`:

- `OutcomeTableTest`: валидация значений/id, defensive copies, операции и конфликты, порядок и snapshots, pure fixtures, фильтр перед весами.
- `WeightedOutcomeResolverTest`: каждый исход наборов 1/2/3/5, границы и соседи через `Math.nextDown/nextUp`, нулевые веса, нормализация и масштабирование, MAX_VALUE/MIN_VALUE, все ошибки и счётчик вызовов.
- В том же resolver test: две независимые `new Random(seed)` для одинаковой последовательности таблиц (включая singleton), одинаковые id и счётчики. Дополнительно фиксированные циклы по небольшим положительным целым весам проверяют принадлежность результата, отсутствие нулевых/исключённых исходов и инвариантность при точном масштабировании на 2. Новая property-testing библиотека и статистические частотные пороги не нужны.

Проверки будущей реализации: `./gradlew :domain:test`, затем `./gradlew :core:classes :lwjgl3:classes`. Существующие tactical tests должны пройти без исправления их ожиданий; diff должен ограничиваться новым пакетом и тестами. Desktop/Android игровой smoke не является проверкой нового визуального поведения: компонент ещё не подключён. В отчёте отдельно указать отсутствие игровой интеграции и любые недоступные проверки.

## Risks / Trade-offs

- BigDecimal создаёт объекты и медленнее double → для обычных 2–3 исходов это разумная цена точных границ; оптимизировать только по измерениям, сохраняя контракт.
- String id допускает опечатки → строгая уникальность и ошибки отсутствующих id, без глобального enum и registry.
- Caller может нарушить физическую фильтрацию или релевантность модификатора → явный протокол, pure fixtures; будущая интеграция обязана отдельно тестировать геометрию и знания существа. Generic picker не может вывести эти правила из весов.
- Очень малые вероятности могут быть недостижимы для дискретного RNG → явно ограничена гарантия, отсутствует обещание бесконечной точности источника.
- Новая библиотека не меняет игру сразу → это согласованная граница proposal; не выдавать readiness планирования за готовую механику.

## Migration Plan

В этом PR создаются только delta-spec, design и tasks; proposal сохраняется как исторический документ PR #38 с исходным списком вопросов. Ответы P1–P6 находятся выше и не означают согласование ещё не проведённого review.

Будущая реализация — отдельный implementation PR после приёмки этих артефактов. Добавление пакета не требует миграции сохранений или существующих API. Rollback — удаление независимого пакета до интеграции; игровое поведение не затронуто. Синхронизация main specs и архивирование выполняются после реализации и приёмки, не в этом PR.

## Open Questions

P1–P6 разрешены на уровне предложенного технического контракта. Противоречий с согласованными направлениями геймдизайна не обнаружено; отдельного запроса на изменение правил нет.

За пределами change остаются формулы и баланс конкретных модификаторов, способы передачи знаний о репутации существам и интеграция с будущим событием столкновения. Они требуют отдельного игрового решения и не блокируют реализацию изолированного API. Схема не утверждает все рабочие правила боевой спецификации v0.3.

## Context

Мотивация и согласованные границы — в [proposal.md](proposal.md). Поведение описывают [creature-detection](specs/creature-detection/spec.md) и [delta creature-patrol](specs/creature-patrol/spec.md). Это план для ревью; реализация ещё не выполнялась.

`CreaturePatrolState` уже хранит общую `WorldGeometry`, маршрут, позицию, цель, направление и остаток паузы. `WorldGeometry.isCirclePathValid` проверяет проход круга; приватный `intersectsSegment` выполняет slab-проверку пересечения замкнутого отрезка с AABB. `FirstScreen.render` сейчас сначала двигает охотника, затем обновляет патруль. `WorldPosition` неизменяем, но сам не проверяет конечность координат.

Архитектурная основа — [ADR-001](https://github.com/andrewdarvell/horror-hunter-game-design/blob/main/docs/architecture/ADR-001-hexagonal-architecture.md), прочитанный в соседней копии design-репозитория. Доменная геометрия не является внешней возможностью: отдельный порт для неё не требуется.

## Goals / Non-Goals

**Goals:** один доменный вызов обновления, который гарантирует порядок проверки и остановки; общий источник геометрии; минимальное расширение существующей модели; воспроизводимый сценарий со стеной.

**Non-Goals:** новая иерархия NPC, универсальные AI-state-machine, perception service, event bus, новые зависимости, порты для математических операций, continuous detection и реорганизация модулей.

## Decisions

### 1. Явная LOS в WorldGeometry

Добавить `boolean hasLineOfSight(WorldPosition from, WorldPosition to)`. Валидировать оба endpoints до обхода препятствий: отсутствие, неконечные координаты и неконечную длину отрезка отклонять через `IllegalArgumentException`. Для каждого AABB вызвать существующий приватный `intersectsSegment`; хотя бы одно пересечение означает `false`. Пустой список означает `true`. Это O(n) по числу препятствий, без дополнительной карты, тактических ячеек и spatial index.

Существующая slab-математика ограничивает параметр отрезка диапазоном [0, 1] и использует `enter <= exit`, поэтому включает касания и endpoints. При нулевом dx или dy уже предусмотрена отдельная ветка без деления. Нулевой отрезок открыт только вне всех замкнутых AABB. Проверить эту семантику непосредственно тестами, включая обратное направление, горизонтальные и вертикальные лучи, тонкие стены, corner touch и луч вдоль границы.

Альтернатива `isCirclePathValid` отвергнута: радиус расширяет зону блокирования, хотя луч проходит свободно; нулевой радиус этот API запрещает. Повторное использование приватной slab-математики сохраняет одну реализацию пересечения. Правило движения «касание круга допустимо» не меняется; для LOS касание блокирует обзор.

### 2. Расширить CreaturePatrolState

Добавить положительный конечный `detectionRadius`, `boolean alerted` и nullable `WorldPosition lastSeenHunterPosition`. До первого обнаружения last-seen отсутствует; после — всегда задан. Публичное представление: `isAlerted()` и `getLastSeenHunterPosition()` с документированным отсутствием значения до обнаружения. Состояние патруля и существующие package-private наблюдения для тестов сохраняются.

Конструктор получает дополнительный обязательный `detectionRadius`. Заменить `update(double)` на `update(double deltaSeconds, WorldPosition hunterPosition)` и обновить все production/test call sites. Не оставлять публичный путь обновления, обходящий обнаружение. Старые тесты патруля передают корректную позицию охотника за пределами радиуса. Новый код проверяет время и позицию до любых изменений, в том числе когда существо уже насторожено. Неконечную относительную дистанцию отклонять до мутации, чтобы ошибки экстремальных координат не зависели от порядка short circuit.

Внутри update:

1. Валидировать входные данные.
2. Считать расстояние через `Math.hypot`, без квадратов, способных переполниться. Сравнить `distance <= detectionRadius`; если условие выполнено, проверить LOS на сохранённом экземпляре `geometry`.
3. При выполнении обоих условий установить `alerted = true` и сохранить текущую позицию охотника. При невыполнении не менять last-seen и не сбрасывать настороженность.
4. Если `alerted`, завершить обновление без изменения позиции, цели, направления и остатка паузы.
5. Иначе выполнить существующий алгоритм движения и ожидания с сохранением остатка времени.

Это работает и при `deltaSeconds == 0`: восприятие обновляется, время патруля не расходуется. Проверка в начале каждого update, включая первый, обеспечивает стартовое обнаружение до начальной паузы. Пересоздание объекта сбрасывает состояние; отдельного reset API нет.

Альтернатива — конкретная обёртка вокруг патруля — добавила бы второго владельца состояния и координацию двух update для одного объекта. Для этого среза расширение существующего класса проще. Переименование модели и выделение общего AI-контракта не требуются.

### 3. Порядок кадра и границы модулей

`FirstScreen` вызывает `updateHunter(delta)`, затем `creaturePatrol.update(delta, hunter.getPosition())`, затем обновляет debug controls и рисует сцену. Внутренний порядок detection → patrol гарантирует `domain`; условие остановки не дублируется в `core`.

Охотник, патруль и LOS используют один `worldGeometry`, созданный экраном; у патруля геометрия уже сохранена. `domain` хранит координаты, считает расстояние и LOS, управляет настороженностью. `core` отвечает за ввод, composition, камеру и графические примитивы. `lwjgl3` и `android` не получают новой логики.

Обновление дискретное: проверка происходит из позиции существа до его шага. Если оно само приблизилось к охотнику во время шага, обнаружение возможно лишь на следующем update. Разные разбиения интервала могут менять момент обнаружения; прежняя эквивалентность разбиений применима только к патрулю без обнаружения. Это явно отражено в MODIFIED delta вместе с нулевым интервалом.

### 4. Представление и воспроизводимая сцена

Сохранить `ShapeRenderer`: до обнаружения существо `CYAN`, после — `RED`; добавить короткий указатель от центра к last-seen. Нормализацию направления для отрисовки выполнять по last-seen, не по текущему охотнику. При нулевой длине не рисовать указатель; цвет продолжает показывать настороженность. Новые ресурсы и disposable-объекты не требуются, существующий `dispose` сохраняется.

Предлагаемая конфигурация тестовой сцены: радиус обнаружения 3.0, маршрут A=(5, 0), B=(5, 1), прежние скорость 2.0, радиус тела 0.3 и пауза 0.5. Существующие AABB и старт охотника (0, 0) сохраняются. Оба waypoint и весь путь справа от стены x=[3, 4], y=[-3, 3] безопасны, стартовая дистанция больше 3.0.

Для ручного сценария подвести охотника к (2.5, 0): для любой позиции этого маршрута расстояние меньше 3.0, но отрезок перекрыт стеной. Затем обойти нижний край стены с запасом для радиуса 0.4 (например, через (2.5, -3.5), (5, -3.5)) и приблизиться к (5, -1): LOS открыта и дистанция до всего маршрута не больше 2.0. После обнаружения уйти обратно за стену, проверить неподвижность и сохранение указателя. Перезапуск сцены даёт повторяемый сброс. Точные координаты — ориентиры проверки, не новые элементы управления.

## Risks / Trade-offs

- Дискретная проверка может пропустить короткое пересечение радиуса между кадрами → не обещать continuous detection; проверить разные интервалы отдельно от регрессий чистого патруля.
- Пограничная floating-point геометрия → использовать существующую slab-математику без произвольного epsilon; покрыть точные касания и близкий свободный луч отдельными примерами.
- Расширение публичного API патруля требует миграции тестов → обновить все call sites, сохранить проверки движения и безопасности маршрута.
- Настороженность необратима в этой встрече → ручные сценарии начинать с пересоздания сцены, без добавления игровой кнопки сброса.
- В core нет тестового фреймворка → автоматические проверки поведения выполнить в domain; порядок интеграции проверить чтением вызова, сборкой и ручным desktop-сценарием. Не добавлять инфраструктуру ради этого среза.

## Migration Plan

После ревью planning обновить доменную геометрию и модель, мигрировать вызовы и тесты, затем подключить представление и конфигурацию сцены. Сохранения и внешние потребители API отсутствуют в scope. При откате вернуть изменения модели и её вызовы вместе.

На этапе подготовки не менять `openspec/specs/`. После реализации, проверок и приёмки синхронизировать delta specs и архивировать change отдельным workflow. Все задачи пока остаются незавершёнными.

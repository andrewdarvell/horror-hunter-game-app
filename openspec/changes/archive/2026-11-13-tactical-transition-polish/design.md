## Context

Мотивация, границы и критерии приёмки находятся в [proposal.md](proposal.md). Это план для ревью; реализация не начата. Новые документы созданы по явно подтверждённому исключению из ограничения `openspec-update-change` на создание отсутствующих артефактов.

Актуальный `FirstScreen` вызывает `WorldSceneState.update`, затем читает доменные позиции для кружков, указателя last-seen и камеры. Поэтому атомарный snap в domain становится экранным скачком в том же кадре. `resize` вызывает `viewport.update(width, height, true)`, что дополнительно центрирует камеру. `WorldSceneState` уже фиксирует обе позиции, `placement` и `TACTICAL` вместе; API и алгоритмы `domain.scene`, `domain.tactical`, `domain.actor`, `domain.world` менять не требуется.

Принятые specs требуют совпадения отображаемых позиций с центрами и следования камеры за фактическим охотником. Delta-specs уточняют эти формулировки в `tactical-mode-entry` и `world-navigation`; актуальные `openspec/specs` до реализации и приёмки не редактируются.

## Goals / Non-Goals

**Цели:** отделить кратковременные визуальные координаты от источника игровых данных; однократно зафиксировать endpoints; определить порядок первого и последнего кадров; сделать расчёт перехода проверяемым без OpenGL.

**За пределами design:** универсальный animation engine, новые зависимости рендеринга, новые порты, изменения planner и обнаружения, боевые действия, клеточное передвижение, выход из tactical. Подробные ограничения перечислены в proposal.

## Decisions

### 1. Изменяется параметр demo, а не модель сетки

В `FirstScreen` `PROTOTYPE_CELL_SIZE` становится `1.0` вместо `2.0`. Origin остаётся `(0, 0)`, `FitViewport` — `20×15`; радиусы тел — `0.4` и `0.3`, обнаружение — `3.0` мировых единицы. Геометрия, начальные позиции, waypoint, скорости и паузы сохраняются. `TacticalGrid` продолжает поддерживать произвольный положительный конечный размер клетки.

Альтернатива — одновременно масштабировать мир или радиус обнаружения — изменила бы gameplay. Поиск planner остаётся 3×3 клетками; его охват в мировых единицах при новой demo-сетке закономерно уменьшается. Не компенсировать это расширением поиска.

### 2. Узкое состояние перехода принадлежит core

Добавить локальный объект `TacticalEntryTransition` в `core`, отвечающий только за два start/end, прошедшее время и вычисление визуальных позиций. Хранить неизменяемые значения координат, а не ссылки на изменяемые векторы камеры. `WorldPosition` допустим как объект значения для чтения; визуальные результаты никогда не передаются в setters, planner или `scene.update`. Объект не владеет `WorldSceneState`, вводом, камерой или графическими ресурсами.

`FirstScreen` выбирает одну пару визуальных позиций на кадр и использует её для всех связанных элементов. Пока переход неактивен, пара берётся непосредственно из domain. `lwjgl3` и `android` используют тот же core без платформенных ветвей. Domain остаётся независимым от libGDX, времени анимации и состояния представления.

Альтернатива с интерполяцией внутри domain нарушает мгновенную фиксацию и freeze. Tween framework или общий animation engine избыточны для одного перехода.

### 3. Порядок кадра исключает начальный snap

В `FirstScreen.render`:

1. Сохранить режим и обе доменные позиции **до** `scene.update`. В exploration это позиции последнего показанного кадра, а на первом render — начальные позиции сцены.
2. Для входного `delta` получить безопасный интервал: конечный неотрицательный интервал оставить, отрицательный, NaN и бесконечность заменить нулём до вызова domain. Контракт самого domain по отклонению невалидных аргументов сохраняется. Нулевой update по-прежнему может обнаружить охотника и инициировать вход.
3. Выполнить ровно один обычный `scene.update` с вводом, сохранив действующий порядок движения, обнаружения и расстановки.
4. Только для смены `EXPLORATION → TACTICAL` с результатом `SUCCESS` создать переход: start — сохранённые позиции, end — новые доменные позиции, совпадающие с центрами из `placement`.
5. В **этом первом кадре** показать start с `elapsed = 0`. Не применять к новой анимации delta обновления, которое вызвало вход: этот интервал предшествовал её запуску. Даже большой delta не пропускает первый кадр.
6. В последующих кадрах продвигать активный переход безопасным delta, затем один раз выбрать визуальные позиции, обновить камеру и отрисовать сцену. Повторные T, `ALREADY_TACTICAL` или отсутствие outcome не пересоздают переход. Доменные tactical-updates остаются неподвижными.

При `NO_VALID_PLACEMENT` или `INVALID_INPUT` анимация не создаётся: сохраняются существующий лог отказа и обычное отображение актуального exploration-состояния. До успешного входа не замораживать отображение и не откатывать движение, выполненное domain.

Альтернатива со start после update уже теряет исходные позиции. Продвижение на полный delta в кадре создания может сразу показать конечный центр и воспроизвести исходное «моргание».

### 4. 220 мс, точные endpoints и один коэффициент

Константа длительности — `0.22` секунды. Для последующих кадров положительный конечный delta ограничивается оставшимся временем; нулевой и невалидный интервал не продвигают анимацию. Сначала ограничить шаг, затем складывать, чтобы большой интервал не породил переполнение.

При `u = clamp(elapsed / 0.22, 0, 1)` использовать `s = u² × (3 − 2u)` и для обеих координат обоих участников `start + (end − start) × s`. Общий коэффициент сохраняет согласованность движения. Smoothstep обеспечивает плавный старт и остановку; линейный lerp даёт заметный излом скорости, а асимптотическое приближение затрудняет точное завершение.

При `elapsed = 0` возвращать **сами start**, при достижении длительности — **сами end**, без повторного вычисления endpoints через lerp. В завершающем кадре сразу допустимо выбрать доменные позиции: они равны сохранённым end и не менялись после успеха. Один и тот же перевод double → float применяется к кружкам и камере. Следующий кадр обычного tactical-render численно совпадает с завершающим; не делать финальный дополнительный snap камеры.

220 мс отсчитываются с первого показанного кадра перехода; создание добавляет максимум один кадр относительно domain-update. При просадке следующий кадр может сразу стать финальным — промежуточные кадры нельзя гарантировать без достаточной частоты рендера. При нулевой дистанции сохраняется тот же жизненный цикл без искусственного движения.

### 5. Камера и resize используют текущую визуальную позицию

Камеру устанавливать в выбранную визуальную позицию охотника на каждом render, без собственного lerp, отдельного таймера или накопления ошибки. Благодаря этому смещение мира согласовано с кружком охотника, включая первый кадр. Вне перехода действует прежнее прямое следование domain.

При положительном resize обновлять viewport без автоматического центрирования (`centerCamera = false`), затем восстановить камеру из текущего визуального состояния и обновить её матрицу. Resize не продвигает время, не вызывает domain-update и не пересоздаёт endpoints. До первого render использовать начальную доменную позицию; нулевой размер игнорировать по прежним правилам. Изменение экранных размеров закономерно меняет проекцию, но не мировую позицию камеры. Zoom и виртуальные размеры не анимируются.

Альтернатива `viewport.update(..., true)` временно подменяет положение камеры центром viewport; дополнительное сглаживание камеры создало бы отставание и скачок при переключении на обычное следование.

### 6. Обязательная тактика и last-seen

С первого кадра после успешного domain-update показывать фиксированную сетку и контуры обеих занятых клеток полностью, без fade. Контуры всегда берутся из `placement`, а не из преобразования визуальных кружков в клетки. G в tactical не скрывает сетку и контуры. Проходимость debug-сетки продолжает рассчитываться существующим способом; не добавлять новую модель общей проходимости разных тел.

Кружки рисуются по выбранным визуальным позициям. Указатель начинается в **визуальной** позиции существа и направлен к неизменной **доменной last-seen**, а не к визуальному или фактическому текущему охотнику. Цвет настороженности читается из domain. При нулевой длине указатель скрывается; вычисления остаются конечными. Хранить новую last-seen или выполнять LOS из визуальных координат нельзя. Это сохраняет смысл `creature-detection`, поэтому отдельная delta этой capability не требуется.

### 7. Проверки разделены по ответственности

В `domain` дополнить существующие `WorldSceneStateTest`, `TacticalEntryPlannerTest` и при необходимости `CreatureDetectionTest` сценариями сетки 1.0: разные безопасные клетки, оба радиуса, проверка центра и пути, отказ и атомарность, неизменные perception/freeze/last-seen. Сохранить проверки иных размеров сетки, особенно 2.0; не заменить все fixtures на новый demo-размер. Проверить реальные demo-параметры для ручного входа и воспроизводимого подхода с открытой LOS.

В `core` настроить JUnit Jupiter 5.13.4 и JUnit Platform по образцу domain, только в test scope. Проверять локальное состояние перехода без OpenGL: start, середину (110 мс), точный end (220 мс), разбиение времени, ноль, отрицательный delta, NaN, бесконечность, большой конечный delta, совпадающие endpoints. Проверка кадра создания с большим delta должна охватывать порядок orchestration в core, а не только чистую формулу. Узкий core-тест с настоящим `WorldSceneState` может подтвердить, что domain уже в центрах, пока визуальные позиции ещё исходные; не переносить тестируемую интерполяцию в domain ради готового test runner.

Desktop-приёмка дополнительно проверяет реальную камеру, resize, сетку, указатель и оба триггера; численные тесты не заменяют отрисовку. Проверки планируются в tasks; ни одна проверка приложения этим design не объявляется выполненной.

## Risks / Trade-offs

- **Start до update отличается от позиции, принятой planner после движения охотника.** → Это сохраняет непрерывность первого кадра. Доменная проверка безопасности относится к отрезку от позиции на момент попытки до центра, а не гарантирует безопасность визуальной хорды от предыдущего кадра. На большом exploration-delta визуальный круг может пересечь препятствие; это ограничение текущего прямого визуального перехода, которое следует отдельно оценить на ревью и ручной приёмке. Domain collision и planner не изменяются; скрыто добавлять маршрут или новые игровые проверки нельзя.
- **Радиус обнаружения выглядит иначе на новой сетке.** → Автотест границы 3.0 мировых единицы и LOS, ручная проверка масштаба; не пересчитывать радиус через cellSize.
- **Новая сетка меняет доступность кандидатов в demo.** → Проверить demo-сценарии на 1.0 без изменения геометрии и расширения поиска; отказ остаётся допустимым по существующему контракту.
- **Первый и последний кадры легко пропустить при интеграции.** → Проверить отдельно создание без продвижения времени, точные endpoints, отсутствие второго сглаживания камеры и отсутствие центрирования при resize.
- **Низкая частота кадров уменьшает число промежуточных изображений.** → Точный конечный результат важнее искусственного продления анимации; первый кадр всё равно показывается с прогрессом 0.

## Migration Plan

После ревью реализовать tasks в рамках этого change: сначала локальный transition-state и тесты, затем подключение к экрану и demo-параметр. Миграций данных, новых runtime-зависимостей и изменений API domain нет.

После проверок и приёмки отдельно синхронизировать delta-specs с main specs и архивировать change. До этого main specs описывают прежнюю реализацию. Откат реализации — вернуть demo-константу и прежний выбор позиций в core вместе с соответствующим контрактом specs; domain-модель и сохранённые данные не затрагиваются.

## Context

Мотивация — в `proposal.md`. Сейчас все 12 production-типов находятся в `domain.world`. `WorldSceneState` вызывает package-private `applyTacticalPosition` у двух участников, а также `checkDetection` и `advancePatrol` у существа. Эти вызовы перестают компилироваться при разделении `scene` и `actor`; подпакеты Java не дают привилегированного доступа.

Предыдущее решение оставить участников в `scene` заменено по результатам пересмотра требований к пакетам. Этот документ — предложение для архитектурного ревью PR #13; разрешение реализации ещё не получено.

## Goals / Non-Goals

**Goals:** сохранить четыре предметных пакета, единый источник текущих позиций, последовательность симуляции и атомарный результат размещения. Публичные операции между пакетами должны иметь явные локальные инварианты и не давать core доступ к состояниям сцены.

**Non-Goals:** менять игровые правила, размер клетки, константы, порядок фаз или анимации; вводить ECS, общий AI framework, новые Gradle-модули, реестр участников или capabilities на вырост. Публичные FQCN и внутренний контракт identity могут измениться; сценарии игры и API координации сцены сохраняются.

## Decisions

### 1. Четыре пакета и направление зависимостей

| Пакет относительно `ru.darvell.game.hhg.domain` | Классы | Ответственность |
| --- | --- | --- |
| `world` | `WorldPosition`, `WorldGeometry`, `StaticAabb` | Пространственные значения, препятствия, коллизии и LOS |
| `actor` | `HunterState`, `CreaturePatrolState` | Данные и поведение участников |
| `tactical` | `TacticalGrid`, `CellCoordinates`, `TacticalPlacement`, `TacticalEntryPlanner`, `TacticalEntryResult` | Сетка и чистое планирование размещения |
| `scene` | `WorldSceneState`, `SceneMode` | Порядок обновлений, владение и переключение режима |

`scene → actor/tactical/world`, `actor → world`, `tactical → world`. Никаких `actor → tactical/scene`, `tactical → actor/scene` или зависимостей нижних пакетов от верхних через сигнатуры/FQCN. `world` ничего не знает об участниках и тактике.

Согласно ADR-001 domain остаётся чистой Java 8 без libGDX, платформ и адаптеров. Core создаёт компоненты, обрабатывает ввод и рисует результат. Дополнительные порты ради перемещения файлов не нужны.

### 2. Что действительно требует интерфейса

Planner сейчас получает позиции, радиусы, grid и geometry, возвращает неизменяемый результат и не обновляет участников. Этой зависимости интерфейс не требуется. Сцена знает конкретного охотника для ввода и конкретное существо для обнаружения; замена этих ссылок общим типом только вынудит добавлять cast или лишние capabilities.

Возможный будущий общий контракт `actor.TacticalParticipant` ограничивается `getPosition`, `getRadius` и подготовкой тактической позиции. В него **не входят** `checkDetection`, `advancePatrol`, alerted, last-seen, ввод охотника или SceneMode. Общая способность быть размещённым не означает способность патрулировать или видеть охотника.

Предпочтительное место такого интерфейса — `actor`: он описывает участника и использует только `WorldPosition`. И `scene`, и, при реальной необходимости, `tactical` могут зависеть от этого нижнего контракта без обратной зависимости actor. Вариант `tactical.TacticalParticipant` с реализациями в actor тоже может образовать DAG, но вводит ненужную сейчас зависимость `actor → tactical`; если planner затем импортирует конкретного actor, появится цикл. В `scene` интерфейс потребует обратной зависимости actor, в `world` смешает геометрию с ролью участника. Отдельный contracts/common пакет не требуется.

Для выбранного решения интерфейс **отложен**: сейчас нет операции, которая реально работает с коллекцией разнородных TacticalParticipant. Конкретные ссылки сцены и скалярные входы planner достаточны. Это не запрет интерфейса в будущем; условие введения — общий потребитель, а не только два похожих метода.

### 3. Почему публичный mutating интерфейс не защищает сцену

Методы интерфейса Java публичные. `void applyTacticalPosition(WorldPosition)` оставляет внешний путь произвольного перемещения; проверка null/finite не подтверждает режим, валидную пару клеток и актуальность плана. Передача публичного успешного результата planner также не подтверждает, что он рассчитан для текущей сцены и текущих позиций.

Даже контракт «не бросать исключения после проверки» не обеспечивает атомарность для произвольной реализации интерфейса: второй участник может бросить исключение после обновления первого или вызвать внешний callback. Сцена не должна считать два вызова mutating интерфейса транзакцией. Общий интерфейс не является механизмом прав доступа.

Проверяемая альтернатива для будущего интерфейса: `TacticalParticipant withTacticalPosition(WorldPosition center)` с контрактом отдельного результата без мутации оригинала; конкретные final-классы могут возвращать свой тип covariant. Сцена готовит все результаты до публикации. Такой контракт всё равно требует проверки реализаций: Java не запрещает реализации нарушить чистоту. Сейчас ограничиваемся двумя известными final-классами, без plugin-модели и injection произвольных участников.

### 4. Выбранный конкретный API: подготовить копии, затем опубликовать

У каждого actor появляется `copy()` и `withTacticalPosition(WorldPosition center)`, возвращающие **новый объект того же конкретного типа**. Старый package-private mutating `applyTacticalPosition` удаляется; публичного эквивалента setter нет. Это небольшое изменение инкапсуляции, а не механическое повышение видимости.

`copy()` точно сохраняет все поля, включая допустимые существующими конструкторами пограничные состояния; не вводит новых проверок, способных запретить ранее допустимое создание сцены. `withTacticalPosition` требует non-null и finite center, меняет только позицию в копии, оригинал остаётся неизменным и при успехе, и при ошибке. Это локальный контракт подготовки состояния, **не** обещание, что позиция уже является допустимым размещением сцены. Проверки клетки, радиуса, пути, препятствий и совместимости пары остаются у planner; actor не импортирует tactical.

Копирование выполняется приватным copy constructor, без повторного запуска обычного конструктора патруля: иначе сбросятся позиция, target index, direction, waitRemaining и обнаружение. Для существа копируются route, geometry, movementSpeed, radius, pauseSeconds, detectionRadius, alerted, lastSeenHunterPosition, position, targetIndex, direction, waitRemaining. Для охотника — position, movementSpeed, radius. Неизменяемые WorldPosition, WorldGeometry и неизменяемый список route можно разделять; независимые изменяемые поля не разделяются.

Сцена копирует входных участников при создании и держит только собственные экземпляры в private-полях. Так retained constructor-ссылки из core не могут менять состояние сцены даже через уже существующие публичные move/update. Getters сцены возвращают значения, не actor. Внешние копии с произвольными позициями не могут быть установлены в уже созданную сцену: setters участников и setters режима/placement не добавляются.

При успешном плане `enterTactical` сначала получает в локальные переменные обе копии, центры и placement. Пока подготовка не завершилась, поля сцены не изменяются. Если подготовка бросит исключение, прежние ссылки, позиции, metadata, mode и placement сохраняются; исключение не маскируется под игровой outcome. На допустимом результате текущего planner локальные проверки не должны отказывать.

После подготовки commit состоит только из присваивания ссылок охотника, существа, placement и mode. Между ними нет вызовов actor, выделения памяти, валидаций, событий или callbacks. При planner failure подготовка не выполняется. Это атомарность наблюдаемого результата в существующей однопоточной симуляции, без обещания thread safety или обработки аварий JVM.

Сцена остаётся единственным владельцем **актуальных** позиций; подготовленные локальные копии не публикуются параллельно. Placement описывает клетки и не превращается в независимо обновляемый источник позиции.

Цена: два новых состояния при создании сцены и два при успешном входе; не на каждом кадре. Identity переданных участников больше не совпадает с внутренними экземплярами, ссылки на них не отражают дальнейшие изменения сцены. Это явно меняемый технический контракт, соответствующий прежнему запрету обновлять участников снаружи после передачи. В core текущие ссылки локальны в конструкторе; проверка всех call sites обязательна.

### 5. Обнаружение и патруль — конкретные семантические операции

| Текущий метод | Решение | Инвариант |
| --- | --- | --- |
| `applyTacticalPosition` у обоих | Заменить на конкретный `withTacticalPosition` | Новый объект, finite center, неизменность оригинала и остальных полей |
| `checkDetection` | Сделать public у CreaturePatrolState | Проверки hunterPosition и расстояния до мутации; прежний LOS/radius, last-seen и признак первого обнаружения; патруль не продвигается |
| `advancePatrol` | Сделать public у CreaturePatrolState | Самостоятельная проверка finite delta >= 0 до мутации, включая alerted; прежний no-op при alerted, маршрут, время и паузы |

Существующие `move` и `update` остаются конкретными публичными операциями. Все допустимые текущие вызовы сохраняют результат. Новая валидация advancePatrol необходима потому, что раньше его предусловия проверял вызывающий код. Эти методы безопасны как операции самостоятельного actor; доступ к actor, принадлежащему сцене, закрывается владением копиями, а не проверкой SceneMode внутри actor.

Интерфейсы восприятия и патрулирования откладываются: сейчас по одной реализации и одному конкретному сценарию координации. При появлении нескольких реально взаимозаменяемых реализаций выделить узкий интерфейс в actor, без зависимости от SceneMode и без объединения способностей. NPC без патруля и союзник без обнаружения не обязаны реализовывать чужие операции. Обобщённый AI и произвольное число участников не входят в этот change.

### 6. Сравнение вариантов

| Вариант | Четыре пакета | Защита размещения | Стоимость / решение |
| --- | --- | --- | --- |
| Public mutating TacticalParticipant | Да | Не защищает парный commit и retained references сам по себе | Отклонён |
| TacticalParticipant с подготовкой копии | Да | Подготовка до commit, при соблюдении контракта реализаций | Возможен; сейчас нет общего потребителя, интерфейс отложен |
| Конкретные copy/withTacticalPosition | Да | Изоляция владения, подготовка без мутации, commit присваиваниями | **Выбран**: без новых интерфейсов, token и coordinator |
| Public concrete setters | Да | Нет защиты от частичной мутации | Отклонён |
| Участники внутри scene | Нет | Сохраняет package-private, но нарушает требуемую структуру | Отклонён |
| Owner-token и two-phase mutating API | Да | Требует проверки всех путей мутации и гарантии non-throw commit | Больше протокола и точек отказа; сейчас не нужен |

Для будущей нечисти, NPC и союзников граница actor уже есть. По появлении общего потребителя интерфейс можно выделить из одинаковых операций подготовки; perception и patrol развиваются независимо. Не обещаем, что текущий planner на двух участников уже обслуживает произвольное число сущностей.

### 7. Сохранить порядок симуляции и проверки

Порядок update остаётся: валидация → ранний выход tactical → движение охотника → checkDetection → попытка входа при первом обнаружении или ручном запросе → advancePatrol, если остался exploration. Нельзя заменить две фазы вызовом creature.update: он продвинет патруль до решения сцены.

Прямой отказ enterTactical не меняет snapshot. Отказ внутри update не откатывает уже выполненные движение и обнаружение; не встревоженный патруль продолжает шаг. Alerted сохраняется, автоматический повтор без первого обнаружения не добавляется. При snap сохраняются metadata патруля и pre-snap last-seen; в tactical обновления заморожены, повторный запрос даёт ALREADY_TACTICAL.

Тесты geometry остаются в world; grid/planner — в tactical; hunter, patrol, detection, копирование и независимость копий — в actor; координация и видимое состояние сцены — в scene. JUnitPlatformSmokeTest остаётся в domain. Диагностические getters патруля остаются package-private в actor.

Проверки metadata из WorldSceneStateTest нельзя оставить на исходном constructor-объекте: он теперь независим от сцены. Точные assertions сохранения всех полей перенести в actor-тесты copy/withTacticalPosition, включая состояние после движения и обнаружения. В scene проверять snapshot через публичные getters, заморозку, last-seen, пару клеток и изоляцию от внешних ссылок. Не выдавать диагностические поля production API ради тестов и не считать старую alias-проверку достаточным тестом состояния сцены.

Package-private fixture TacticalEntryPlannerTest.blockedCentersExcept, используемую тестом сцены, заменить локальной private test fixture с той же геометрией. Не открывать production helpers ради переноса тестов.

### 8. OpenSpec

`skip_specs: true` сохраняется: игровые требования не меняются, delta specs и новая capability не нужны. Архитектурные контракты и изменение технического владения описаны здесь и в proposal, проверяемые работы — в tasks. Основные openspec/specs остаются без изменений.

## Risks / Trade-offs

- Ручное копирование может потерять скрытое состояние → тесты всех полей и независимости копий после нескольких фаз патруля/обнаружения; приватный copy constructor без повторной инициализации.
- Изменяется identity и появляется аллокация → явно описать в PR, проверить все call sites; аллокация только при создании/успешном переходе, копирование не переносить в покадровый update.
- Подготовка ошибочно мутирует оригинал → actor-тесты успеха и отказа; ни одного mutating вызова между присваиваниями commit.
- Публичные фазовые методы могут использоваться вне сцены → независимые проверки входа и изоляция принадлежащих сцене объектов. Отдельный режим внутри actor не вводится.
- Интерфейс в будущем может нарушить чистоту подготовки → вводить с реальным потребителем и contract tests; Java interface не доказывает этот инвариант.

## Migration Plan

После архитектурного ревью и отдельного разрешения реализации: baseline и перечень тестов, перенос четырёх пакетов, отдельный diff copy API/владения/публичных фаз, адаптация тестов, сборка и регрессии из tasks. Не создавать временные production-дубликаты и совместимые wrappers старых FQCN.

Откат — обратный тематический commit; миграции данных нет. В текущем PR меняются только planning-документы. Реализация, sync/archive и новые игровые возможности не запускаются до приёмки владельцем.

# Разделение обнаружения и начала боя

Решения E1–E6 предложены для согласования в planning PR.

## Контекст

Сейчас `WorldSceneState.observeContact()` использует результат `CreaturePatrolState.observeHunter()` как условие автоматического входа. При успешной расстановке состояние уже `CHASE`, но движение прерывается до первого хода погони. Тот же критерий обнаружения входит в `hasThreat()` для бесплатного safe exit и оплаченного breakout. Мотивация и границы change описаны в [proposal](proposal.md).

## Решения

### E1. Два порога по центрам

На одном снимке живых H (охотник) и C (существо) получаем `d = hypot(H.x − C.x, H.y − C.y)`, LOS по замкнутому отрезку между центрами и сумму радиусов тел `s`.

| Проверка | Положительный результат |
| --- | --- |
| Detection | Оба живы, LOS открыта, `d ≤ detectionRadius` |
| Engagement | Detection положителен и `s ≤ d ≤ engagementRange` |

Сравнения включительные, без дополнительного допуска на пороге. Касание тел разрешено, касание AABB лучом закрывает LOS. Промежуток между поверхностями круга не нужен как отдельная характеристика. Расстояние по центрам согласуется с detection и остаётся независимым от сетки. Нижняя граница исключает вход из пересечения тел. Pure-проверка engagement не обновляет наблюдение.

Добавить в immutable `CreatureBehaviorConfig` обязательный `engagementRange` с условием `0 < engagementRange < detectionRadius`, оба числа конечны. Явно задать параметр у всех мест создания экземпляра. Копирование, получение урона и размещение сохраняют config. При `engagementRange < s` контакт физически недостижим для этой пары, при равенстве доступен в точке касания. Сумма зависит от обоих участников и проверяется на снимке.

Demo-профиль сохраняет detection **3,0**, радиусы тел H **0,4**, C **0,3**, скорости PATROL/CHASE/SEARCH/RETURN **2,0 / 4,0 / 3,0 / 2,0**, скорость H **5,0 world units/s**, SEARCH **2,0 с**, паузу на waypoint **0,5 с** и сетку **1,0**. Engagement равен **1,5 world units**. Второй профиль только для проверок отличается engagement **2,0**.

### E2. Движение в CHASE до контакта

Detection по-прежнему обновляет `alerted` и `lastSeenHunterPosition`, сохраняет прогресс PATROL и переводит существо в CHASE. Между порогами сцена остаётся в exploration. Существо движется прямо к позиции, увиденной на последнем замере, до ближайшей доступной точки пути. При чистом луче у узкого места тело может остановиться перед AABB и оставаться в CHASE. При потере видимости по радиусу или LOS включается прежний SEARCH к last-seen, затем RETURN к сохранённому участку. Замер после движения C предшествует финализации SEARCH. Охотник может увеличить отрыв на **1,0 world unit/s** на открытом прямом пути.

В `FirstScreen` использовать существующие «Преследует», «Ищет», «Возвращается к патрулю» и указатель last-seen. Успех engagement виден по существующему переходу к tactical; при отказе использовать текущий результат размещения. Demo-маршрут и карта подходят для проверки E6 без изменения стартовой сцены.

### E3. Снимки, порядок и одна попытка на границу

В `WorldSceneState` заменить единственную память контакта двумя значениями последнего замера, detection и engagement. До исходного замера оба false. В каждой точке на одной паре фактических позиций сначала обновить восприятие, потом сравнить engagement с предыдущим результатом и сохранить обе оценки до вызова planner. Только engagement false → true инициирует auto-entry, в том числе при непрерывной видимости. Снимок после отказа остаётся true до отрицательного замера. Краткое пересечение порога или закрытие LOS целиком между замерами событий не создаёт.

Один исходный замер выполняется до движения, в том числе при первом `delta=0`. Затем каждый полный шаг **10 мс** идёт в порядке **ход H → замер → ход C → замер → завершение SEARCH**. Auto-entry пробуется на положительном фронте сразу после соответствующего замера, до следующего действия. Если оба порога пересечены на одном замере, CHASE и last-seen фиксируются до planner. Успех прекращает exploration, сохраняет позиции перед snap и отбрасывает остаток exploration-интервала. Отказ сохраняет выполненные наблюдение и движение. Сохранить накопитель и направление незавершённого шага.

Ручной запрос T или control использует тот же planner независимо от обоих порогов. Прямой доменный `enterTactical()` сохраняет возможность немедленного запроса без exploration-замера. Совпавший с ещё необработанным ручным запросом auto-entry покрывает оба запроса одной попыткой, включая отказ. При отсутствии исходного auto-entry ручной запрос обрабатывается после первого хода H, а при отсутствии полного шага — после исходного замера, если он требовался. Каждый последующий зафиксированный фронт engagement обрабатывается самостоятельно, в том числе после разрыва и повторного контакта между ходами H и C одного шага. Snap, availability, preview и кадры presentation контактов не создают.

### E4. Safe exit и B4/B5

На фактических центрах и текущих клетках, либо на подготовленном endpoint breakout, определяем bite adjacency. Это одна из восьми соседних клеток с открытой LOS и живыми участниками независимо от фазы укуса. Через закрытую LOS ни одна из трёх проверок угрозы не положительна. При живом H и без живого C все проверки угрозы отрицательны.

| Команда | Условие, удерживающее живого охотника в tactical | Результат вне угрозы |
| --- | --- | --- |
| Бесплатный safe exit | Detection или bite adjacency | SUCCESS без расхода времени |
| Breakout после полной оплаты D (B4) | Engagement или bite adjacency | ESCAPED, даже при detection |

Бесплатный выход сохраняет запрет ухода от видимого преследователя, в том числе при ручном входе без alerted. Engagement входит в detection, поэтому новый порог уже покрыт этой проверкой. Отдельное условие B4 позволяет после оплаченного манёвра снова бежать, пока преследователь ещё видит H. Если после полного D остаётся хотя бы одна из двух угроз breakout, вернуть `MOVED_STILL_TACTICAL` с оплаченным временем. Равенство engagementRange удерживает в tactical при открытой LOS. Соседство удерживает даже при `d > engagementRange`, а пересечение зоны по пути не добавляет реакции B1–B3. Условия REJECTED, INTERRUPTED, цена, origin-first укус, полный swept path, приоритет смерти и preview/commit остаются по B1–B3.

При safe exit, ESCAPED и победном выходе подготовить базовые значения detection/engagement из фактических позиций без вызова `observeHunter()` и опубликовать их вместе с режимом. На успешном safe exit оба false. При ESCAPED engagement false, detection может быть true. Это базовые значения для следующего замера, а `alerted`, last-seen, поведение и поисковый таймер сохраняются такими, какими были в tactical. Нулевой update после выхода без ручной команды ничего не меняет. Первый полный шаг даёт ход H, затем применяет его результат к восприятию. Видимый H обновляет last-seen и возвращает или продолжает CHASE. Невидимый H при сохранённом CHASE запускает SEARCH по памяти, при сохранённом SEARCH используется его остаток. Повторный вход B5 следует только за новым engagement false → true и может произойти уже на следующем полном шаге. Дополнительного ожидания между боями нет.

### E5. Коллизии и история встречи

Exploration сохраняет существующий sweep AABB и живого тела для обоих участников. `TacticalEntryPlanner` сохраняет размер поиска и порядок выбора пары. Допустимая опубликованная пара занимает разные клетки, круги в центрах не проникают друг в друга, каждый snap проходит полную действующую проверку статической геометрии. Для произвольного cellSize фильтровать совмещённые пары по `d ≥ s` до ранжирования. Snap атомарен, промежуточные визуальные позиции не участвуют в физике. Обычный tactical шаг использует существующий sweep с неподвижным живым телом при сохранении отказа OCCUPIED для его клетки и BLOCKED_PATH для проникновения вдоль отрезка. Для demo даже ближайшая диагональ между свободными клетками отстоит от центра другого тела на `1 / √2 > 0,7`. B3 уже исключает проникающий путь прорыва.

Расстановка и переходы публикуются после подготовки полного результата. Tactical и presentation не продвигают exploration AI и его таймеры. Exploration, вход и бесплатный выход не тратят tactical units. При повторном входе сохраняются HP, cumulative tactical time, текущая фаза укуса с остатком и последний immutable результат без replay событий. Укус впервые инициализируется только при первом входе с живым C. Новые восприятия в exploration обновляют память штатно. Победный HIT автоматически выводит в exploration, тело исключается из engagement, detection, движения и occupancy, ручной hunter-only вход доступен.

Геометрия, правила и состояния остаются в чистом Java `domain`. `core` задаёт demo config, показывает доменный результат и проводит ввод через существующие controls. Новых портов, AI-состояний, pathfinding, каналов восприятия, cooldown и системы способностей нет. [ADR-001](https://github.com/andrewdarvell/horror-hunter-game-design/blob/main/docs/architecture/ADR-001-hexagonal-architecture.md)

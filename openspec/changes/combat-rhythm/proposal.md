# Change: combat-rhythm

## Why

Первый ручной playtest `first-tactical-attack` выявил неприятный сценарий: охотника замечают близко к существу, он естественным образом подходит на соседнюю клетку, **немедленно получает укус за шаг**, а затем за двухединичный замах может получить ещё два укуса. Охотник с 4 HP погибает до второго удара, даже если игрок выбирает логичные действия. Это не баг арифметики: текущий `WorldSceneState.resolve` намеренно разрешает укус на каждой целой единице времени, как было утверждено для первого прототипа. Проблема — отсутствие **читаемого ритма и возможности тактически ответить**, а не недостаточное количество HP.

Следующий минимальный срез — **телеграфирование угрозы, подготовка укуса и восстановление после атаки** текущего прототипного существа. Охотник должен понимать, когда рискованно подходить, когда можно отступить и когда появляется окно для собственного удара. Сохранить опасность прямого столкновения, но убрать гарантированную безвыходную «мясорубку».

Это продолжение направления из [дизайна боя](https://github.com/andrewdarvell/horror-hunter-game-design/blob/main/docs/game-design/exploration-and-combat.md): осмысленный выбор, условная длительность действия, автоматическое разрешение реакций за время действия, отсутствие кнопки «конец хода», маневрирование важнее обмена HP.

## What Changes

### 1. Узкий ритм для одного прототипного врага

- Вместо правила «укус за каждую единицу времени в досягаемости» хранить в domain **ограниченное состояние цикла укуса** текущего существа: готовность/подготовка (читаемая угроза), удар, восстановление. Точный набор значений и единицы времени определить в design, не вводя общий AI state machine всех врагов.
- Время состояния изменяется **только при принятых тактических действиях**, а не при `render(delta)` или ожидании выбора команды.
- На момент входа в tactical исходное состояние должно быть предсказуемым. Если охотник подходит к врагу с расстояния одного-двух шагов, первый шаг не должен автоматически гарантировать урон без ранее читаемой угрозы. Но если существо действительно уже готово к укусу при начале сцены, это должно быть явно показано: не выдавать бесплатную безопасность вслепую.
- Переход между подготовкой, ударом и восстановлением должен давать **хотя бы один достижимый тактический ответ**: отойти из зоны, использовать безопасное окно для своей атаки или заставить тварь потратить действие. Нельзя просто заменить каждый укус на скрытую задержку, которую игрок никак не видит.
- Фаза угрозы должна иметь определённую привязку к позиции: с какой клетки/направления атакует существо и когда проверяется досягаемость/LOS. Не вводить без объяснения ни самонаводящийся удар через всю карту, ни автоматическое обнуление угрозы каждым шагом охотника. Planning обязан разобрать, фиксируется ли цель/направление на телеграфе или проверяется текущая доступность при разрешении, и последствия обоих вариантов.
- Восстановление должно реально исключать повторный укус в этот интервал; длинный замах охотника может пересечь несколько стадий, и resolver должен корректно отработать их в хронологическом порядке.

### 2. Реакции внутри существующего автоматического resolver

- Сохранить цикл: `player intent → auto resolution (time + creature response) → immutable result → visual feedback → next decision`.
- Не вводить пошаговое ручное управление существом, кнопку «ждать», инициативу, общий scheduler или новый combat engine. Продолжить использовать узкое состояние `WorldSceneState` и явные команды `tryMoveHunterTo` / `tryAttackCreature`.
- Планировать взаимодействие с текущими длительностями **шаг = 1**, **атака = 2** условные единицы. Это временные числа первого прототипа. Если предлагаемый ритм требует изменить их, оформить как **отдельный выбор для утверждения**, а не незаметно менять существующий баланс.
- Приоритет эффектов в одной точке времени (сейчас эффект охотника перед реакцией врага), ранение, поражение и прерывание остаются определёнными и тестируемыми. При смерти существа никакого запоздалого укуса. При смерти охотника оставшаяся часть действия прекращается с фактической стоимостью времени.
- Отказ команды не меняет ни время, ни состояние врага, ни HP/placement; заранее рассчитанный результат и вся информация о фазе должны публиковаться атомарно. Доменное время не должно зависеть от анимаций 220/180/240 мс.

### 3. Читаемое предупреждение, в том числе для touch

- До команды игрок должен **видеть текущую фазу угрозы и ориентировочно понимать её последствия**: подготовка / атака скоро / восстановление. Минимум — текстовая и цветовая индикация в текущем HUD; возможно выделить угрожающую клетку или направление, если выбран направленный удар.
- Разрешённое действие не должно внезапно причинять урон, о котором не было доступного предупреждения в состояниях, где игрок способен его избежать. Если возможен риск на действии длительностью 2 единицы, HUD должен показывать риск, а не только «Атаковать · 2 ед.».
- Touch/mouse: сохранить tap по свободной соседней клетке для шага и отдельный tap по существу для выбора атаки, затем кнопку. Новых обязательных клавиш, hover или меню из четырёх секторов не добавлять.
- Текущий `TacticalAttackResult` хранит упорядоченные `Effect.BITE/HIT`, а `FirstScreen.showResolution` — строку событий; расширение результата может понадобиться для предупреждения/подготовки/восстановления. Не вычислять фазу из цветов/длительности анимации в core. Не использовать краткую 240-мс плашку как единственный источник критически важной информации — актуальная фаза должна оставаться видимой до следующего выбора.
- Новые нажатия по-прежнему игнорируются во время entry, move и attack presentation. Никакого replay удержания.

### 4. Отдельно проверить обнаружение, не смешивая две проблемы

- В playtest существо оказывается близко в момент обнаружения. `CreaturePatrolState` уже имеет detection radius **3.0 world units**, LOS и поведение авто-входа; пользовательское ощущение «заметил за одну клетку» может быть следствием геометрии, положения патруля и момента пересечения порога, а не доказательством ошибки радиуса.
- В этом change **не менять** радиус обнаружения, LOS, патруль, геометрию, скорость exploration, размер клетки или выравнивание tactical. Добавить воспроизводимый сценарий входа с соседней клеткой и с большей дистанцией, проверить что проблема ритма решается без скрытой подстройки detection.
- Если playtest покажет самостоятельную проблему позднего обнаружения, вынести её в отдельный change с критериями и сравнением ситуаций.

## Non-goals

Новые монстры и их универсальная политика атак, полноценные AI-графы, передвижение врага по клеткам, сложные намерения, дистанционные атаки, оружие, уклонение/защита как новые действия, характеристики/стамина/AP, RNG, вероятности попадания, изменение HP 4/2 и урона 1, лут, смерть/выход из tactical, прорыв, глобальное время exploration, анимация спрайтов, новый UI framework.

## Capabilities

### Modified Capabilities

- `tactical-attack`: цикл укуса, разрешение длинного действия, атомарный результат, постоянный телеграф и предупреждение о риске атаки.
- `tactical-movement`: продвижение того же цикла за принятый шаг, уход от укуса и атомарная публикация состояния врага вместе с перемещением.

Новая самостоятельная capability не требуется. `tactical-mode-entry` уже делегирует реакции в `tactical-attack`; размещение, detection и presentation входа не меняются. Инициализация цикла при входе определена в delta `tactical-attack`.

Planning в `design.md`, `specs/` и `tasks.md` — **предложение для архитектурного ревью**. Решения G1–G6 из design требуют утверждения владельцем; наличие файлов и успешная CLI validation не означают утверждение или разрешение реализации.

## Planning decisions requiring review

1. **Фазы и длительности.** Какой конкретно минимальный цикл; сколько условных единиц длится подготовка и восстановление; действует ли состояние только в радиусе укуса или сохраняется после выхода из него.
2. **Телеграф.** Фиксированная клетка/направление или проверка актуальной соседности при ударе. Как игрок может безопасно отойти, но не бесконечно эксплуатировать состояние.
3. **Порядок событий.** Когда начинается подготовка относительно окончания шага; если действие охотника на 2 единицы пересекает момент укуса, что происходит при совпадении сроков; что если цель погибла в тот же момент.
4. **UI.** Минимальная постоянная индикация фазы/угрозы и понятная подсказка рядом с кнопкой атаки, не зависящая от mouse hover.
5. **Играбельность.** Как на исходных 4/2 HP добиться возможности победить правильным позиционированием и таймингом, сохранив возможность проиграть при неосторожности. Привести пошаговые трассы минимум для: сближения, попытки двух атак подряд, отступления перед укусом и удара во время восстановления.

Все предложенные числовые параметры нового ритма — кандидаты до утверждения design. Не выдавать их за принятый баланс. Codex должен предложить **одну рекомендуемую модель** и, при необходимости, одну альтернативу с объяснением, после чего явно выделить решения владельца.

## Acceptance Criteria

1. Из тактического входа на дистанции двух клеток охотник может подойти к существу, заранее узнать об угрозе и сделать осмысленный выбор до первого возможного укуса. Соседство при входе отдельно покрыто и не гарантирует незаявленный укус.
2. Есть проверяемый вариант выиграть у текущего врага с исходными 4 HP против 2 HP с помощью разумных шагов и моментов атаки, без обязательного повышения HP и без эксплойта «бесплатных» действий. Есть и путь поражения за неосторожный выбор.
3. В domain явная фаза укуса и её время/условия, а не таймер в core; состояние сохраняется между командами, но не прогрессирует от кадров или простого ожидания решения.
4. Для принятых `tryMoveHunterTo` и `tryAttackCreature` все эффекты пересечения фаз/времени вычисляются и публикуются единожды; обе команды сохраняют прежние правила допустимости, LOS, радиуса и занятости. Отказ полностью неизменен.
5. Указана и протестирована семантика телеграфа при выходе охотника из зоны, блокировке LOS, повторном входе, перемещении в соседнюю диагональ и длинной команде на две единицы. Не допустить удара из явно недоступной позиции или через препятствия.
6. В хронологическом порядке корректно разрешаются поражение существа, поражение охотника, приоритет эффектов, остановка при смертельном укусе; нет повторных или отложенных укусов после исчезновения угрозы.
7. HUD показывает фазу и читаемую угрозу до выбора действия, в том числе при mouse/touch и после resize; результат перечисляет факты подготовки, укуса, восстановления и удара в правильном порядке. Core не решает, когда атаковать существу.
8. Сохраняются FPS-independent tactical time и прежние 220-мс вход, 180-мс шаг, 240-мс показ атаки, FitViewport, touch pointer, single busy gate и отсутствие replay. Никаких новых команд в период presentation.
9. Domain tests: детерминированные последовательности, пограничные совпадения времени, длинный удар, отказ, смерть, позиционная доступность, начальное состояние и повторы. Core tests: фаза в HUD, выбор цели, busy, pointer/resize и presentation. Desktop воспроизводимый smoke + **ручной playtest** двумя сценариями (ошибка и удачная тактика), с verification.md.
10. Domain остаётся чистой Java 8, core — libGDX, `WorldSceneState` владеет изменениями, без универсального scheduler/AI engine. OpenSpec strict validation, domain/core tests, lwjgl3 classes, Android debug сборка при доступном SDK, diff check.

## Notes for Codex

- Сверь `WorldSceneState.resolve`, где укус сейчас начисляется в конце **каждой** единицы, и `TacticalAttackResult.Effect`, который знает только BITE/HIT; не делай изменения исключительно в HUD.
- Это gameplay change после ручного тестирования, а не исправление неверного расчёта урона. Не завышать HP/понижать damage как обход проблемы.
- Подготовь `design.md`, нужные delta-specs и `tasks.md` после мерджа proposal. Сначала review решений о фазах/телеграфе, затем отдельный implementation PR.

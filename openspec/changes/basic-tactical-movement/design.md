## Context

Мотивация и границы находятся в [proposal.md](proposal.md). Документ подготовлен для архитектурного ревью; реализация не начинается. Создание недостающих planning-артефактов выполняется по ранее согласованному для этого workflow исключению.

`WorldSceneState` владеет копиями участников и неизменяемым `TacticalPlacement`. `update` в tactical намеренно не выполняет свободную симуляцию. `HunterState.withTacticalPosition` уже подготавливает копию охотника; `WorldGeometry.isCirclePathValid` проверяет весь отрезок движения круга со статическими AABB и допускает касание без проникновения. Эти механизмы достаточны для шага без изменения алгоритмов геометрии или первоначального входа.

В core `FirstScreen` хранит одну визуальную пару координат и `TacticalEntryTransition` для входа за 220 мс; камера и resize используют визуального охотника. Pointer input пока отсутствует. В core уже настроен JUnit Jupiter: отдельный backend для численных тестов не нужен.

Новая capability `tactical-movement` описывает правила шага. Дельты существующих capabilities устраняют абсолютный запрет перемещения после входа и ограничивают старые требования о времени и диагональной скорости свободным exploration. Main specs до реализации и приёмки остаются без изменений.

## Goals / Non-Goals

**Цели:** одна явная доменная команда, однозначная экранная клетка назначения и локальная сериализация через занятость представления. Gameplay-позиция и занятость публикуются сразу; время визуального движения принадлежит только core.

**За пределами design:** AP, инициатива, враг, бой, action wheel, pathfinding, маршрут из нескольких клеток, очередь команд, универсальные акторы и animation engine. Сохраняются четыре пакета domain и Java 8. Android runtime не является условием приёмки; совместимый pointer API обязателен.

## Decisions

### 1. Сцена применяет отдельную команду

Добавить `WorldSceneState.tryMoveHunterTo(CellCoordinates target)` с возвращаемым enum `TacticalMoveResult` в `domain.tactical`. Результаты: `SUCCESS`, `NOT_TACTICAL`, `INVALID_INPUT`, `SAME_CELL`, `NOT_ADJACENT`, `OCCUPIED`, `BLOCKED_CENTER`, `BLOCKED_PATH`. Исключения для обычной недоступной клетки не нужны. Метод не принимает delta, экранные координаты или визуальную позицию и не вызывает `update`, planner, патруль или восприятие.

Порядок проверок фиксируется для детерминированного отказа: режим; отсутствие target; совпадение с текущей клеткой; соседство; занятость существом; представимость центра/смещения; безопасность центра; безопасность полного пути. При нескольких нарушениях возвращается первое по этому порядку. `NOT_TACTICAL` допустим и для null target вне tactical; остальные результаты проверяются в tactical.

Обе координатные разности вычислять после расширения к `long`: `dx = (long) target.x - current.x`, аналогично y. Условие `max(abs(dx), abs(dy)) == 1` не должно использовать переполняющееся вычитание int. `CellCoordinates` уже хранит int: внешние значения вне диапазона отсекаются в core до преобразования, а прямой domain-вызов с противоположными пределами получает `NOT_ADJACENT`.

Для допустимого по соседству target получить центр той же сеткой. Неконечный центр/длина смещения либо центр, который не отображается обратно в целевую клетку без насыщения координат, дают `INVALID_INPUT`. Не менять общие API `TacticalGrid` ради одной команды; защитные вычисления локальны операции. Источник — текущая фактическая позиция охотника, уже совпадающая с центром `placement.hunterCell` по инвариантам сцены.

Подготовить `preparedHunter = hunter.withTacticalPosition(targetCenter)` и новый `TacticalPlacement(target, placement.creatureCell)` до записи в сцену. После всех проверок и подготовки вместе опубликовать обе ссылки без callbacks или промежуточных наблюдателей. При отказе сохраняется весь снимок сцены, включая прежний экземпляр placement. Это атомарная публикация в существующей однопоточной модели сцены, а не новое обещание thread safety. Существо не копируется и не меняется. Первоначальная атомарная подготовка обоих участников в `enterTactical` сохраняется.

Альтернатива с разблокировкой WASD смешивает свободную физику и клеточную команду. Публичные setters либо возврат изменяемых акторов нарушили бы владение. Интерфейс команд, command bus и общий action framework для одного метода не нужны.

### 2. Диагональ разрешает фактическая геометрия

Проверить отдельно центр назначения через `isCirclePositionValid` и полный прямой путь из текущего доменного центра через `isCirclePathValid`, с собственным радиусом охотника. На demo это 0.4; радиус не вшивается в алгоритм. Касание без проникновения допустимо, как при входе. Свободная LOS между центрами не доказывает допустимость пути круга.

Восемь направлений равно допустимы по соседству. Не требовать свободных ортогональных клеток у диагонали: их центры могут быть заблокированы, хотя конкретный диагональный коридор безопасен для круга. Если диагональ проникает в угол AABB, отказывает проверка полного пути. Не искать обход, не скользить вдоль стены и не выбирать другую клетку автоматически.

Занятость означает запрет **целевой** клетки существа. Новая динамическая circle-circle collision между телами этим срезом не вводится; статическая безопасность и раздельная занятость сохраняют принятую модель. Геометрический путь и источник шага совпадают с визуальным отрезком: в отличие от входа, дополнительного exploration-движения до команды нет.

### 3. Один pointer down — одна попытка без очереди

`FirstScreen` регистрирует узкий `InputAdapter` в `show`, обрабатывая `touchDown(screenX, screenY, pointer, button)`. Принимается pointer 0 с `Input.Buttons.LEFT` — та же кнопка передаётся для touchscreen. Hold, drag и touchUp движения не создают; другие кнопки и дополнительные pointers игнорируются. Локальный флаг primary-down сбрасывается по соответствующему touchUp, чтобы удержание и повторное событие без отпускания не стали ещё одной командой. Игнорируемое во время busy нажатие тоже потребляется до отпускания; оно не переигрывается после завершения перехода.

До преобразования координат проверяются: экран активен, размеры/viewport готовы, scene в tactical и ни вход, ни шаг не анимируются. Обработка выполняется сразу в callback на render thread, без pending target и без очереди. Успех сразу создаёт визуальный переход, поэтому второй touchDown в том же пакете событий уже видит busy. В exploration pointer-событие игнорируется даже если в последующем render сработает T или обнаружение. Событие в кадре, который ещё должен закончить старую анимацию, также игнорируется; принимать можно только новое нажатие после показанного конечного кадра.

По [контракту InputProcessor](https://libgdx.com/wiki/input/event-handling) события mouse/touch доставляются перед render на render thread. Это позволяет не добавлять синхронизацию domain. WASD/T/G продолжают опрашиваться прежним способом. В `hide`/`dispose` экран снимает свой handler и восстанавливает прежний, только если текущим всё ещё является его handler; сбрасывает primary-down. Не затирать handler другого экрана и не вводить InputMultiplexer без нескольких реальных потребителей.

Альтернатива polling `isTouched` дала бы автоповтор. Агрегат `justTouched` хуже различает pointer/button и последовательность нескольких событий; очередь скрыто выполнила бы тап после того, как игрок видел busy.

### 4. Hit testing до unproject, в одной системе экранных единиц

Выделить небольшой core-helper выбора клетки с зависимостями от действующих `Viewport` и `TacticalGrid`, без зависимости domain от libGDX. До первого положительного resize ввод недоступен. Нулевой resize помечает pointer-геометрию неготовой до следующего положительного resize, не меняя камеру, domain или время перехода.

Использовать screen-координаты события и размеры `Gdx.graphics.getWidth/getHeight`, соответствующие режиму экрана; не смешивать их с `getBackBufferWidth/Height` на HiDPI. Bounds viewport берутся из `getScreenX/Y/Width/Height` после актуального resize. Для input с началом сверху перевести только границы прямоугольника: `left = screenX`, `top = graphicsHeight - screenY - screenHeight`, `right = left + screenWidth`, `bottom = top + screenHeight`. Принимать `left <= x < right` и `top <= y < bottom`, также проверяя границы самого окна. Вычислять суммы границ безопасно, без переполнения int. До unproject отсекаются поля, нулевые размеры и устаревшая после некорректного resize геометрия; координаты не clamp-ятся к краю карты.

После проверки вызвать `viewport.unproject` на копии исходного `(screenX, screenY)`: y вручную не переворачивать. Этот метод уже учитывает bounds и камеру; повторный flip или `camera.unproject` без bounds дал бы другую клетку. Конвенция проверена по [Viewport 1.14.2](https://github.com/libgdx/libgdx/blob/1.14.2/gdx/src/com/badlogic/gdx/utils/viewport/Viewport.java) и [Camera.unproject 1.14.2](https://github.com/libgdx/libgdx/blob/1.14.2/gdx/src/com/badlogic/gdx/graphics/Camera.java).

Проверить конечность мировых координат, вычислить floor координат клетки относительно origin/cellSize в double и проверить диапазон int **до** вызова существующего `worldToCell`. Не полагаться на насыщающее Java-преобразование double → int. Пограничная мировая координата принадлежит начинающейся там клетке по прежнему контракту; искусственный epsilon не добавляется. Преобразование отражает фактически полученное float-значение unproject.

Камера в момент выбора уже соответствует последней визуальной позиции; при idle она совпадает с доменным центром. Положительный resize сохраняет `viewport.update(..., false)` и немедленное восстановление камеры по визуальной позиции, чтобы picking и render использовали одну матрицу. Не вычислять мир вручную через отношение размера окна к 20×15. Основание подхода — [официальная документация Viewport](https://libgdx.com/wiki/graphics/viewports).

### 5. 180 мс для шага, 220 мс для входа

Сохранить существующий локальный механизм двух визуальных позиций: у `TacticalEntryTransition` оставить прежний constructor для входа на 0.22 секунды и добавить именованную factory `forHunterMove(hunterStart, hunterEnd, creaturePosition)` с фиксированными 0.18 секунды и совпадающими start/end существа. Внутренний constructor принимает длительность, доступную только этим двум случаям; не добавлять интерфейсы клипов, timeline или произвольные animated properties. Одна активная ссылка transition обслуживает вход или движение и обеспечивает единый busy gate.

Для шага start снимается до `tryMoveHunterTo`, когда визуальные и доменные позиции совпадают. End читается после `SUCCESS`. В обоих случаях применяется smoothstep `s = u²(3 − 2u)`, точные start при нуле и end при завершении. Ортогональный и диагональный шаг имеют одинаковую длительность; диагональный визуально проходит больший отрезок, что допустимо для одного клеточного действия без модели AP или скорости tactical-движения. Старое правило нормализации скорости относится к exploration.

Поскольку pointer callback предшествует render, ввести локальный признак `transitionJustCreated`. В первом render новой анимации, независимо от места создания (callback движения либо успешный вход внутри update), таймер не продвигается; признак снимается после выбора исходных позиций. Только следующие render расходуют безопасный delta. Это предотвращает съедание первого кадра интервалом, предшествующим команде. При большом следующем delta переход заканчивается точно, при нуле/отрицательном/неконечном — не продвигается. Повторный T не меняет endpoints или таймер.

Сразу после принятия шага выбрать start для визуального охотника, оставить существо на месте; при завершении выбрать доменные позиции и очистить transition. Камера всегда получает ту же выбранную позицию охотника, без собственного lerp. Resize не создаёт и не завершает анимацию. Не телепортировать визуального охотника к следующей цели: дополнительные команды отбрасываются, пока transition активен, включая первый кадр и ещё не показанное завершение.

### 6. Назначенная клетка — видимый отклик на успех

Уже существующий контур `placement.hunterCell` перемещается в цель с первого кадра успешного шага. Этого выделения достаточно для MVP; дополнительный hover, preview, меню и toast не требуются. Контур существа и обязательная сетка не меняются. Отклонённая цель не подсвечивается как принятая и не запускает анимацию; нормальный отказ не логируется как ошибка приложения.

Настороженность, last-seen, патруль и восприятие сохраняются. Указатель по-прежнему начинается в визуальном существе и направлен на сохранённую last-seen; он не сопровождает перемещающегося охотника. Повторный вход T не заменяет текущий placement и не возвращает охотника в первоначальную клетку.

### 7. Проверки до реализации определены по слоям

Domain-тесты вызывают команду без libGDX: восемь направлений, повторные шаги, все результаты отказа, целиком неизменный снимок при отказе, разные размеры сетки/радиусы, крайние int-координаты, безопасный центр при небезопасном пути, касание и диагональный коридор. Сохранить тесты входа и независимости акторов; не ослаблять их ради новой команды.

Core-тесты проверяют реальную численную `Viewport.unproject`, а не собственную подменяющую формулу. Использовать `Viewport.setScreenBounds`, тестовый Graphics и актуальную матрицу камеры; OpenGL-context не нужен. Если операции матриц требуют gdx natives, добавить только test-runtime desktop natives уже используемой версии, загрузить их в тесте и не переносить рендеринговую логику в domain. Отдельно проверить core-обработчик pointer-событий и общую orchestration с настоящей сценой, первый render без advance, busy на кадре завершения, отсутствие replay удержания, восстановление input handler.

Тестовые экраны: 640×480 без полей; 1000×600 с pillarbox 100 px слева/справа для мира 20×15; 800×800 с letterbox 100 px сверху/снизу; нечётный размер с асимметричным округлением полей. Проверить границы half-open, углы, смещённую камеру, отрицательные мировые координаты и resize между последовательными кликами. Отдельно проверить несовпадающий размер backbuffer при тех же логических screen-координатах.

## Risks / Trade-offs

- **Старые freeze-тесты и specs запрещают все движения.** → Уточнить условие «без принятой отдельной команды», сохранив неподвижность от WASD/времени/T и замороженные патруль/восприятие; в world-navigation отдельно ограничить правила времени и диагональной скорости exploration.
- **События доставляются до render.** → Одноразовый флаг создания сохраняет первый кадр, а busy проверяется при получении события, не после продвижения таймера.
- **Picking на границе чувствителен к float и HiDPI.** → Одна система экранных единиц, реальный unproject, явные поля и half-open bounds, отсутствие epsilon/clamp и проверки int до cast.
- **Глобальный input handler может пережить экран.** → Регистрация/снятие привязаны к lifecycle, проверяется владение текущим handler.
- **Название TacticalEntryTransition становится шире одного входа.** → На этом срезе сохраняется тип и узкая factory шага с двумя фиксированными случаями; общее переименование или animation framework не требуется.
- **Нет очереди и отдельного сообщения об отказе.** → Быстрые taps во время движения намеренно теряются; немедленный контур принятой клетки отличает успех. Это явный контракт MVP.

## Migration Plan

После архитектурного ревью реализовать доменную команду и тесты, затем picking/input в core, расширение локального transition и интеграцию. Публичные контракты первоначального входа не заменяются; миграций данных нет. Откат среза удаляет pointer-команду и возвращает прежний запрет движения между клетками, сохраняя реализованный вход за 220 мс.

Проверки и отчёт находятся в tasks. Main specs синхронизируются, а change архивируется только после реализации и приёмки отдельным действием.
